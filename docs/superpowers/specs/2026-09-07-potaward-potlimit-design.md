# 팟 분배 · 팟리밋 계산 — 설계

- **날짜**: 2026-09-07
- **범위**: PRD §10 2단계 — PLO8 격자의 남은 두 칸
- **상태**: 설계 승인 대기
- **선행**: 1단계(격자 뼈대 · 진행절차 · 승자 판독) 완료, `main` 머지됨

## 1. 무엇을 만드나

PLO8 행의 두 칸을 연다.

| 칸 | 무엇을 묻나 | 상호작용 | 정답 출처 |
|---|---|---|---|
| **팟 분배** | 이 팟(절반)의 임자는 누구인가 | 퀴즈 · 좌석 지목 | `buildPots` · `awardPots` |
| **팟리밋 계산** | 지금 최대 얼마까지 걸 수 있나 | 퀴즈 · 숫자 입력 | `pl` 룰셋의 `maxRaiseTo` |

두 칸을 **한 하위 프로젝트로 묶는다**(사용자 확인 2026-09-07). PRD §10 이 2단계로 함께
묶어 둔 대로다. 다만 둘은 기술적으로 독립이라 원자도 화면도 서로를 모른다 — 아래 §3·§6 의
원자 둘은 각각 따로 서고, 한쪽이 막혀도 다른 쪽은 간다.

**드릴마다 재미 게이트를 따로 받는다.** 둘을 함께 만든다고 해서 함께 통과시키지 않는다.

## 2. 층 구조 — 엔진이 포트를, 게임 층이 어댑터를

지금 `lib/games` 와 `lib/simulator` 는 **서로를 모른다**(프로덕션 코드에 import 가 한 줄도
없다 — `integration.test.ts` 만 건넌다). 이 설계가 그 사이에 첫 간선을 놓으므로 방향을
먼저 정한다.

```
lib/simulator/evaluate.ts   HandEvaluator 타입 (포트)  — awardPots 는 이것만 받는다
lib/games/evaluator.ts      evaluatorFor(spec)  (어댑터) — spec.eval 을 읽어 원자를 고른다
```

**방향은 `games → simulator` 한 쪽뿐이다.** 엔진은 "핸드를 매기는 무언가"라는 모양만 알고,
그 모양을 이 종목에 맞게 채우는 것은 게임 층의 일이다. 반대로 놓으면 엔진이 `GameSpec`
을 알게 되어 ADR-003(게임 데이터의 정본은 `lib/games` 하나)이 무너진다.

## 3. 원자 A — `evaluatorFor(spec)`

```ts
// lib/simulator/evaluate.ts (포트)
export type HandEvaluator = {
  rankHi(hole: Card[], board: Card[]): HandRank
  /** null 이면 이 종목에 로우가 없다. 있어도 성립하지 않으면 호출이 null 을 낸다 */
  rankLo: null | ((hole: Card[], board: Card[]) => LowRank | null)
}

// lib/games/evaluator.ts (어댑터)
export function evaluatorFor(spec: GameSpec): HandEvaluator
```

**`spec.eval` 만 읽어 갈린다.** 표시 라벨도 `spec.id` 도 읽지 않는다(전역 제약 4).

| `spec.eval` | `rankHi` | `rankLo` |
|---|---|---|
| `mustUse = {hole:2, board:3}` · `lo = {a5, 8}` | `bestOmahaHi` | `bestOmahaLow(…, 8)` |
| `mustUse = {hole:2, board:3}` · `lo = null` | `bestOmahaHi` | `null` |
| `mustUse = null` · `lo = null` | `evaluateHand([...hole, ...board])` | `null` |
| `mustUse = null` · `lo != null` | — | **던진다** |

넷째 줄(강제 조합 없는 하이로우)은 **플랍게임에 존재하지 않는다.** 해당하는 종목은
스터드/8·라즈뿐이고 그것들은 `family !== 'flop'` 에서 이미 걸린다. 도달할 수 없는 조합이지만
조용히 하이만 평가하는 대신 던지게 둔다 — 언젠가 도달한다면 그것은 새 스펙이 잘못됐다는 뜻이다.

셋째 줄이 **지금 `awardPots` 가 하는 일 그대로다**(`pots.ts:129`). 그래서 노리밋 홀덤
(`/rush`)은 이 확장을 거쳐도 답이 한 글자도 바뀌지 않는다 — 그것이 이관의 안전줄이다.

**`family !== 'flop'` 이면 던진다.** 스터드·라즈는 공유 보드가 없어 `(hole, board)` 라는
시그니처 자체가 성립하지 않는다. 조용히 틀린 답을 내는 것보다 낫다 — 승자 판독 설계 §6
이 세운 규율을 그대로 잇는다.

### 3-1. 승자 판독을 이 원자로 옮긴다

`lib/drills/winner/generate.ts` 는 지금 `bestOmahaHi`·`bestOmahaLow` 를 **직접 부르고**
`spec.eval.mustUse === null` 이면 던진다(`generate.ts:120`). 그대로 두면 "이 종목에서
핸드를 어떻게 매기나"가 승자 판독과 `awardPots` 두 곳에 살게 된다 — 이 레포가 반복해서
경고한 「사본은 갈라진다」가 정확히 그 모양이다.

**이관은 이 설계의 일부다.** 기존 승자 판독 테스트가 이관 뒤에도 그대로 통과하는 것이
이관의 검증이다. 동작은 바뀌지 않아야 한다.

## 4. `awardPots` 확장 — 하이로우 분배

시그니처가 바뀐다.

```ts
awardPots(pots, hole, board, buttonSeat, evaluator): PotAward[]
```

`PotAward` 에 `half: 'hi' | 'lo'` 를 더한다. 같은 좌석이 두 절반을 다 받으면 지급 줄이
둘 생기고, 화면은 「3번 하이 4,100 · 3번 로우 4,000」으로 갈라 보여야 한다.

### 4-1. 팟 하나를 나누는 절차 — 홀칩은 두 번 생긴다

**1단계 · 임자 집합 둘을 구한다** (이 팟의 자격자 중에서만)

- `hiSet` = 하이 최고 동률 좌석들. **동점이면 여러 명 = 하이끼리 스플릿**
- `loSet` = 자격(8 이하)을 통과한 것 중 최저 동률 좌석들. **동점이면 여러 명 = 로우끼리
  스플릿**. 자격자가 하나도 없으면 빈 집합

자격자가 한 명뿐인 팟은 쇼다운이 없다 — 지금처럼 그 좌석이 전액을 받는다(보드가 5장이
아닌 채 끝난 핸드에서 평가기를 부르면 카드가 모자라 던진다).

**2단계 · 팟을 절반으로 가른다 — 홀칩 1차**

- `loSet` 이 비었으면 **하이가 전부 가져간다**(스쿱). 가르지 않는다
- 아니면 `ODD_CHIP_UNIT`(100) 단위로 반 가르고, **홀수 칩이 남으면 하이 절반에** 얹는다

  > 출처: `docs/references/mixgame-facts.md` — 「홀칩은 **Hi 승자에게**」(가이드 p5).
  > 예: 8,100 → 하이 4,100 / 로우 4,000

**3단계 · 각 절반을 그 집합 안에서 나눈다 — 홀칩 2차**

- 절반 금액을 인원수로 나누되 100 단위, 남는 칩은 **버튼 왼쪽 첫 자격자부터** 한 칩씩
- 지금 `pots.ts:144-153` 이 하는 그대로다. **재구현하지 않고 재사용한다** (TDA 2024
  「20: Awarding Odd Chips」 대조가 끝난 코드다)

### 4-2. 여섯 경우가 전부 떨어진다

| 하이 | 로우 | 결과 |
|---|---|---|
| 1명 | 없음 | **스쿱** — 전액 |
| 1명 | 1명 | 반반, 남는 칩은 하이 |
| N명 동점 | 없음 | 전액을 N분할, 홀칩은 버튼 왼쪽부터 |
| N명 동점 | 1명 | 하이 절반을 N분할 · 로우 절반 1명 |
| 1명 | M명 동점 | 하이 절반 1명 · 로우 절반을 M분할 = **쿼터링** |
| N명 동점 | M명 동점 | 각 절반을 각각 분할 |

**한 사람이 하이와 로우를 다 먹는 경우**(같은 좌석이 두 집합에 모두 있음)도 절차상
자동으로 맞는다 — 두 절반 모두 그 좌석에 지급되어 합계가 전액이 된다. 이것도 「스쿱」
이지만 **1행과 원인이 다르다**(로우 불성립 vs 한 사람이 양쪽 최고). 화면 근거 문구를
갈라야 한다.

### 4-3. 사이드팟이 있으면 팟마다 반복한다

**`hiSet`·`loSet` 을 팟마다 다시 구한다.** 팟마다 자격자가 다르기 때문이다. 메인팟에서는
로우가 성립했는데 사이드팟 자격자 중에는 로우가 없어 그 팟만 스쿱이 되는 판이 실제로
나오고, **그것이 이 드릴에서 가장 어려운 문제다.**

### 4-4. 불변식 (테스트로 박는다)

- 지급 합계 == 팟 합계 (한 칩도 새거나 늘지 않는다)
- 모든 지급액은 `ODD_CHIP_UNIT` 의 배수
- 지급 좌석은 그 팟의 자격자 집합 안에 있다
- 로우 없는 종목(`rankLo === null`)에서는 `half: 'lo'` 지급이 하나도 없다

## 5. 팟 분배 드릴

- 라우트: `/games/plo8/potaward` — `routes.ts` 의 `plo8.potaward` 를 채운다
- 화면: **`RushScreen` 그대로.** `renderQuestion` 이 완전히 위임돼 있어 뼈대를 고칠 일이
  없다. 복사하지 않는다
- 기록 키: `plo8.potaward.best` (`<gameId>.<drillId>.best` 규약)

### 5-1. 문제 유형 넷 — 전부 좌석 지목

| 유형 | 묻는 것 |
|---|---|
| `hihalf` | 하이 절반의 임자는 누구인가 |
| `lohalf` | 로우 절반의 임자는 누구인가 (「로우 없음」이 정답인 판을 섞는다) |
| `oddchip` | 반으로 가르고 남는 칩은 누구에게 (정답: 하이 승자) |
| `sidepot` | 이 사이드팟의 임자는 누구인가 (자격자가 갈린다) |

정답은 좌석 **집합**이다 — 동점이면 여러 좌석이 정답이고, 승자 판독과 같은 모양이다
(`answerSeats: number[]`).

**단순 스플릿 유형은 만들지 않는다.** 승자 판독이 이미 그것을 묻는다. 이 드릴의 차별점은
**자격(사이드팟)과 홀칩 순서**에 있다.

### 5-2. 승자 판독과의 경계

승자 판독은 「이 판의 임자」를, 팟 분배는 「**이 팟의** 임자」를 묻는다. 사이드팟이 없고
동점도 없는 판에서는 둘이 같은 질문이 된다 — 그래서 이 드릴의 출제는 **자격이 갈리거나
동점이 있는 판으로 치우쳐야 한다.** 생성기가 그 비율을 보장한다(§8).

## 6. 원자 B — `pl` 룰셋

`Ruleset` 인터페이스에는 이미 `maxRaiseTo(ctx)` 가 있고, `nlh` 는 `ctx.seatBet +
ctx.seatStack`(= 올인)을 돌려준다(`nlh.ts:47-49`). 팟리밋은 여기가 달라진다.

### 6-1. `BettingContext` 에 `pot` 을 더한다

**지금 `BettingContext` 에 팟 금액이 없다.** 그래서 `maxRaiseTo` 가 팟을 알 방법 자체가
없다 — 인터페이스 변경이 불가피하다.

```ts
/**
 * 지금 테이블 위의 돈 전부 — 가운데로 수거된 팟 + **모든 좌석 앞에 놓인 칩**.
 * 자기 자신이 이번 라운드에 낸 것도 포함한다. 팟리밋 산식이 「콜한 뒤의 팟」을
 * 쓰므로 앞에 놓인 칩을 빼면 답이 틀린다.
 */
pot: number
```

`nlh` 는 이 값을 읽지 않는다 — 기존 동작이 그대로다.

### 6-2. 산식 — 자료 정본

> **팟벳 = 마지막 배팅을 콜 하는 데 필요한 금액 + 콜 한 후에 팟에 있는 금액**
> (가이드. `mix-room.html` 프로토타입이 인용한 원문)

콜한 뒤의 팟에는 **방금 넣은 콜도 들어 있으므로 콜 금액이 두 번 더해진다.**

```
callAmt     = ctx.currentBet - ctx.seatBet
maxRaiseTo  = ctx.currentBet + ctx.pot + callAmt
            → 스택 상한으로 자른다: min(위, ctx.seatBet + ctx.seatStack)
```

앞에 벳이 없으면 `callAmt = 0` 이고 팟벳은 팟 금액 그대로가 된다 — **공식은 하나다.**

**회귀 예제(가이드 원문):** 팟 60,000 에 40,000 벳이면
`40,000 + (60,000 + 40,000) = 140,000`. 이 값을 테스트에 박는다.

### 6-3. `RulesetId` 에 `'pl'` 을 더한다

`RulesetId = 'nlh' | 'pl'`. `pl` 은 `minRaiseTo`·`canReopen`·`validateAction`·
`interpretChipPush` 를 `nlh` 와 공유하고 **`maxRaiseTo` 만 다르다** — 팟리밋에서도 최소
레이즈와 리오픈 규칙은 같기 때문이다. 공유는 **위임**으로 한다(복사하지 않는다).

## 7. 팟리밋 드릴

- 라우트: `/games/plo8/potlimit` — 이 칸은 `drillsFor` 가 `spec.betting === 'PL'` 일
  때만 낸다(이미 그렇게 돼 있다). 노리밋 홀덤에는 이 칸이 아예 없다
- 화면: `RushScreen` 그대로 · 기록 키 `plo8.potlimit.best`
- **답은 숫자 직접 입력이다.** 4지선다가 아니다

  > 프로토타입의 근거: 「팟리밋에서는 벳 크기가 선택이 아니라 계산이다. 그래서 숫자를
  > 직접 받는다」(`mix-room.html`). 보기를 주면 계산하지 않고 고를 수 있게 된다.

  입력칸 선례는 `sidepots` 문제의 `PotField { label, answer }` 다.

### 7-1. 문제 유형 둘 — 프로토타입 그대로

| 유형 | 상황 | 묻는 것 |
|---|---|---|
| `potbet` | 앞에 벳이 없다(프리플랍이면 BB 만) | 팟벳을 하면 얼마인가 |
| `potraise` | 앞선 벳이 화면에 놓여 있다 | 팟까지 레이즈하면 얼마를 내는가 |

**벳을 화면에 실제로 칩으로 놓고 묻는다.** 팟리밋 계산은 머리로 그리는 일이 아니라
테이블에 있는 칩을 세는 일이다 — 프로토타입이 세운 지점이고 그대로 잇는다.

금액은 `action-rush/money.ts` 의 `BLINDS`·`unitFor`·`roundUnit` 을 재사용해 그 블라인드
레벨에 실제로 있을 법한 값으로 만든다. 새로 만들지 않는다.

## 8. 테스트 전략

| 대상 | 어떻게 |
|---|---|
| `evaluatorFor` | 승자 판독 **기존 테스트가 이관 뒤에도 통과**하는 것이 검증이다 |
| `awardPots` 하이로우 | 독립 오라클로 재계산해 맞춘다 (`oddchip.order.test.ts` 방식) |
| `awardPots` 불변식 | §4-4 넷을 시드 다수에 대해 검사 |
| `/rush` 회귀 | 노리밋 홀덤 답이 **한 글자도 바뀌지 않아야 한다** |
| `pl.maxRaiseTo` | 가이드 예제 140,000 을 회귀로 박고, 스택 상한·`callAmt=0` 경계 |
| 두 드릴 생성기 | 정답을 화면이 아니라 엔진으로 다시 구해 대조 |
| 출제 분포 | 팟 분배는 자격이 갈리거나 동점인 판의 하한을 보장한다 (승자 판독의 `LO_PRESENT_MIN` 방식) |

**브라우저 확인은 매번 한다.** 지난 두 세션 모두 코드 리뷰를 통과한 결함이 브라우저에서
잡혔다(React `key` 누락, `6번(6번) 콜` 문구).

## 9. 지금 만들지 않는 것

- **앤티를 팟리밋 계산에 포함할 것인가** — PLO8 에 앤티가 없어 해당 없다. 가이드는
  「앤티는 프리플랍 팟 계산에서 제외하는 것이 보편적(대회사마다 다를 수 있음)」이라고만
  한다. 앤티 종목이 붙을 때 정한다 (PRD §11)
- **픽스리밋 `raiseCap`** — 읽는 코드를 쓰지 않는다
- **`/rush` 를 격자로 이관** — 447개 테스트가 걸려 있고 얻는 것이 없다. 노리밋 홀덤의
  두 칸은 계속 `/rush` 를 가리킨다
- **딜링 룸 · 사고 처리** — PRD §10 4단계
- **스터드·라즈** — `evaluatorFor` 가 `family !== 'flop'` 에서 던지는 것이 지금의 사실이다

## 10. 열린 질문

1. **팟 분배 제한시간** — 초안이 필요하다. 기존 `/rush` 는 사이드팟 45초 · 메인팟 지급
   40초 · 홀칩 20초다. 하이로우가 얹히면 늘어야 하는지는 재미 게이트에서 정한다
2. **팟리밋 제한시간** — 숫자 입력은 고르기보다 느리다. 마찬가지로 게이트에서 정한다
3. **팟 분배 좌석 수** — 사이드팟이 성립하려면 올인이 필요하다. 승자 판독의 4좌석으로
   충분한지, 늘려야 하는지
