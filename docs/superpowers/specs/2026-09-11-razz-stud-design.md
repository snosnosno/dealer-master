# 라즈 — 진행절차와 승자 판독 설계

> **날짜**: 2026-09-11 · **범위**: 라즈 다섯 칸 중 **둘** (진행절차 · 승자 판독)
> **선행**: `f101a42` 라즈 스펙이 격자에 붙어 있다. 칸은 하나도 안 열려 있다.

## 0. 왜 이 둘인가

PLO8 1단계가 진행절차와 로우 판독을 **함께** 잡은 이유를 그대로 잇는다 — 자기주도(절차)와
퀴즈(판독)는 상호작용 형태가 정반대라, 뼈대가 **둘 다** 견디는지 한 번에 드러난다. 하나만
만들면 뼈대가 그 하나에 맞춰 굳는다 (PRD §10).

스터드는 플랍게임과 두 가지가 다르다. **카드가 좌석에 열린 채로 놓이고**, **첫 액션을
버튼이 아니라 카드가 정한다.** 이 둘이 같은 결함의 앞뒤다 — 아래 §1 이 그 진단이다.

## 1. 진단 — 카드에 앞뒤가 없다

2026-09-11 스파이크(`spike/razz-grid`)가 격자의 입구를 전부 두드려 얻은 결과다.

**스펙만으로 선 것**: 타입 등록은 `tsc` 가 `routes.ts` 한 곳만 잡았고, `drillsFor` 가
다섯 칸을 냈고(픽스리밋이라 팟리밋 칸이 스스로 사라졌다), `stepsFor` 가 21스텝을 냈고,
홈에 스터드 구획이 저절로 생겼다. 단위 테스트 712개가 그대로 통과했다.

**격자는 맞았다.** 문제는 한 층 아래다.

```
GameSpec.streets[0].deal = { down: 2, up: 1, board: 0 }   ← 스펙은 앞뒤를 안다
                    ↓
deal.ts:52  const n = street.deal.down + street.deal.up    ← 여기서 잃는다
            seats[i].hole = [...seats[i].hole, ...take(n)]
                    ↓
SeatState = { hole: Card[], revealed: boolean }            ← 좌석 통째로 하나
```

그래서 **「누가 제일 높은 카드를 열었나」를 물을 방법이 없다.** 답할 재료가 전달되지
않는다. `firstToActSeat(firstToAct, buttonSeat, seatCount, folded)` 의 서명에 카드가
없는 것은 그 결과다 — 미구현 가지가 아니라 **답을 담을 수 없는 서명**이다.

다만 재설계는 아니다. 호출부 둘(`judge.ts:22`, `deal.ts:99`) 모두 그 시점에 좌석 카드가
이미 스코프 안에 있다 — `dealHand` 가 카드를 먼저 돌리고 나서 베팅을 대본으로 만든다.

## 2. 결정 — 카드에 앞뒤를 붙인다

세 갈래를 놓고 골랐다.

| 갈래 | 값 | 왜 아닌가 / 왜인가 |
|---|---|---|
| A. 좌석에 `up: Card[]` 배열을 하나 더 | 읽는 쪽이 단순 | **딜 순서를 잃는다.** 7번가 엎은 카드가 3번가 엎은 둘 뒤에 그냥 붙는다. 진행절차 드릴이 「몇 번가에 무엇이 내려갔나」를 보여주는 드릴이라 치명적 |
| C. 좌석 밖에 `faceUp: boolean[]` 마스크 | 기존 22곳이 안 깨진다 | **두 배열의 길이가 어긋날 수 있고 컴파일러가 아무 말을 안 한다.** `families.ts` 주석이 적어 둔 그 실패 양식 — 손으로 관리하는 표가 어긋난다 |
| **B. 카드에 앞뒤를 붙인다** ← **채택** | 딜 순서 보존 · 배열 하나 · 어긋날 자리 없음 | 22곳이 한꺼번에 컴파일 에러가 된다. **의도된 것이다** — 2단계 Task 7 의 `BettingContext.pot` 전례(「옵셔널로 만들어 피하지 마라」)를 그대로 따른다 |

**C 는 지금 싸고 나중에 비싸다. B 는 지금 비싸고 그걸로 끝난다.**

## 3. 원자 — `DealtCard`

```ts
// lib/simulator/types.ts
export type DealtCard = { card: Card; faceUp: boolean }
```

- `SeatState.hole: DealtCard[]`
- `HandScript.seats[].hole: DealtCard[]`

**`revealed` 는 남긴다.** 「앞면인가」(`faceUp`)와 「지금 공개됐나」(`revealed`)는 다른
질문이다. 라즈 7번가는 엎어서 주고 쇼다운에 열린다. 화면은 `faceUp || seat.revealed` 로
그린다 — `Seat.tsx` 의 「노출의 유일한 기준은 `revealed`」 규율은 **엎은 카드에 대해**
그대로 살아 있다.

카드만 필요한 곳을 위해 헬퍼 하나:

```ts
export function cards(dealt: readonly DealtCard[]): Card[]
```

`hole` 을 읽는 22곳(테스트 포함 40곳) 대부분이 이 헬퍼로 기계 치환된다. **`tsc` 가 목록을
준다.** 옵셔널로 만들어 피하지 않는다.

### 딜이 앞뒤를 붙인다

`deal.ts` 가 `street.deal.down` 장을 `faceUp: false` 로, `up` 장을 `faceUp: true` 로
붙인다. 순서는 자료대로 **다운 먼저** — 3번가는 엎어 둘, 열어 하나.

## 4. 첫 액션이 카드를 본다

서명을 넓힌다. 좌석을 통째로 받되 이 함수가 필요한 것만 받는다:

```ts
export function firstToActSeat(
  firstToAct: FirstToAct,
  ctx: {
    buttonSeat: number
    seats: readonly { hole: readonly DealtCard[]; folded: boolean }[]
  },
): number
```

`left-of-bb` · `left-of-button` 두 갈래는 `ctx.seats.length` 와 `folded` 만 읽으므로
**동작이 안 바뀐다.** 기존 테스트가 그것을 지킨다.

### 새 원자 — 부분 핸드 비교기

업카드는 1~4장이라 5장 평가기(`evaluateHand`)를 쓸 수 없다. 그런데 자료가 못 박아 뒀다:

> **"가장 높은 업카드"는 줄임말이다 — 실제로는 보드에 뜬 족보 순서다** (사용자 확인 2026-09-02).
> 예 — `4♥ 4♦ Q♠`(4 페어)가 `7♠ Q♥ A♣`(A 하이)보다 먼저 액션한다.

그래서 **1~4장짜리 부분 핸드를 비교하는 원자**를 세운다. 두 방향이 필요하다:

| 원자 | 쓰는 곳 | 규칙 |
|---|---|---|
| `compareUpcardsHi(a, b)` | 라즈 3번가 브링인 (`highest-upcard`) | 포카드 > 트리플 > 투페어 > 원페어 > 하이카드. **업카드는 최대 4장이라 스트레이트·플러시가 성립하지 않는다** |
| `compareUpcardsLo(a, b)` | 라즈 4번가 이후 (`lowest-hand`) | A-5 잣대. A 가 최저, 스트레이트·플러시 무시, 페어는 나쁘다 |

`lowest-upcard`(7카드 스터드) · `highest-upcard-by-suit`(Hi/Lo Regular) 는 **이번에
구현하지 않는다.** 라즈가 쓰지 않고, 자료도 없다(무늬 우열). 기존 `throw` 를 남긴다.

## 5. 평가기 — 포트를 넓힌다

**라즈는 하이가 아예 없는 첫 종목이다.** 포트가 그것을 표현하지 못한다:

```ts
export type HandEvaluator = {
  rankHi(hole: Card[], board: Card[]): HandRank        // ← 필수
  rankLo: null | ((hole, board) => LowRank | null)
}
```

`rankHi` 를 `rankLo` 와 대칭으로 넓힌다:

```ts
rankHi: null | ((hole: Card[], board: Card[]) => HandRank)
```

**그러면 `pots.ts:157` 의 `ev.rankHi(hole[seat], board)` 가 컴파일 에러가 된다.** 의도된
것이다 — 「하이 임자 없음」을 처리하지 않은 유일한 자리를 컴파일러가 짚어 준다.

### `awardPots` 가 로우 전용을 견딘다

지금은 하이가 늘 있다고 전제한다. 로우 전용에서 고쳐야 할 세 줄:

1. `hiSeats` — `rankHi === null` 이면 빈 배열
2. 절반 가르기 — 하이 임자가 없으면 **가르지 않는다.** 로우가 팟 전부를 가져간다.
   홀칩 1차(`splitHalf`)가 돌 자리가 없다 (나눌 층이 하나뿐이다)
3. 자격자 한 명인 팟의 `half: 'hi'` 라벨 — 로우 전용에서는 `'lo'` 다

**팟 분배 칸은 이번에 안 연다**(§8). 이 셋은 포트를 넓힌 대가로 따라오는 최소 가드다.

### 새 원자 — 7장 중 최고 5장

```ts
export function bestFiveLow(cards: Card[], qualifier: 8 | null): LowRank | null
```

C(7,5) = 21 조합 중 최저. `evaluateLowA5` 를 재사용한다 — **잣대와 고르기를 한 함수에
넣지 않는다**(`lowball.ts` 주석의 규율). `qualifier: null` 이면 자격 검사가 없다.

`evaluatorFor` 에 `family === 'stud'` 갈래가 열린다:

```ts
{ rankHi: null, rankLo: (hole) => bestFiveLow(hole, lo.qualifier) }
```

스터드 하이(7카드 스터드·Stud/8)는 **이번에 안 만든다.** `hi: 'standard'` 인 스터드는
기존 `throw` 를 남긴다.

## 6. 승자 판독이 라즈에서 무엇을 묻는가

**라즈는 자격이 없어 로우가 항상 성립한다.** 「로우 없음」이라는 답이 존재하지 않는다.
그런데 지금 생성기는 한 판 10문제를 이렇게 배분한다:

```ts
LO_PRESENT_MIN = 3   // 로우 성립 판의 하한
LO_ABSENT_MIN  = 2   // 로우 불성립 판의 하한 — 매번 있으면 아무도 「로우 없음」을 안 누른다
```

**라즈에선 이 축이 통째로 무의미하다.** 변주 축을 바꾼다 — 「로우가 성립하나」가 아니라
**「무엇을 가르치는 손인가」**:

| 유형 | 가르치는 것 | 하한 |
|---|---|---|
| 스트레이트·플러시가 낀 손이 이긴다 | 라즈는 그 둘을 **무시한다**. `5-4-3-2-A` 가 최고 패다 | 2 |
| 페어가 낀 손이 진다 | 페어는 로우를 망친다 | 2 |
| 나머지 | 평범한 비교 | — |

동점(스플릿)은 **걸러내지 않는다** — 승자 판독 설계가 세운 규율(쿼터링도 안 걸렀다)을
그대로 잇는다. 다만 **목표로 삼지도 않는다**(자연히 나오는 대로 둔다).

`asksFor(spec)` 는 `spec.eval` 에서 나오므로 라즈는 `{ hi: false, lo: true }` 가 된다.
`generateWinnerRun` 의 두 `throw` 가 그 자리에서 열린다.

**화면**: `WinnerQuestionPanel` 이 하이 줄과 로우 줄을 따로 그린다. 라즈는 **로우 줄
하나만** 그린다. `asks.hi === false` 를 화면이 읽어 갈라야 한다 — 지금은 늘 둘이다.
`e2e` 의 `getByRole('button', {name:'1번'}).first()` 가 「하이 줄이 먼저」라는 DOM 순서에
기대고 있으므로(알려진 것) 그 테스트를 함께 본다.

**보드가 없다.** `WinnerQuestion.board` 는 라즈에서 빈 배열이고, 좌석마다 7장이 선다.
쇼다운이므로 7장을 다 보여준다 — 이 드릴에는 앞뒤 구분이 필요 없다.

## 7. 자료에 없어 사용자가 정한 것

| 값 | 정한 값 | 출처 |
|---|---|---|
| 앤티 | 100 | **사용자 확인 2026-09-11** |
| 브링인 | 500 | **사용자 확인 2026-09-11** |
| 스몰벳 | 1,000 | **사용자 확인 2026-09-11** |
| 빅벳 | 2,000 | **사용자 확인 2026-09-11** |

스몰벳이 PLO8 의 BB 1,000 과 같아 두 종목의 칩 그림이 한 세계로 읽힌다. 앤티는 스몰벳의
10%, 브링인은 절반 — 통상 비율이다. 전부 기존 칩 단위(100/500/1,000/…)로 쌓인다.

`deal.ts` 의 `SMALL_BLIND`/`BIG_BLIND` 상수는 **종목별 강제 베팅**으로 바뀌어야 한다.
`spec.forced` 가 `'blinds'` 냐 `'ante+bringin'` 이냐로 갈린다.

### 동률은 출제하지 않는다

3번가 브링인이 동률(같은 랭크의 최고 업카드 둘)이면 무늬로 갈라야 하는데 **자료가 없다** —
`mixgame-facts` **§2 7-Card Stud 절**이 이미 「동률의 무늬 우열은 7카드 스터드 기준으로 자료에 없다 · 프로토타입은 동률 상황을
출제하지 않는다」로 판정했다. 생성기가 그 판을 버리고 다시 뽑는다 (`MAX_TRIES` 전례).

## 8. 안 하는 것

- **팟 분배 · 사고 처리 · 액션 판정 칸** — `routes.ts` 의 `razz` 는 두 칸만 연다
- **7번가 스텁 부족(커뮤니티 카드)** — 사고 처리 드릴 소관이고, 플랍게임 사고 자료가
  없어 그 드릴 자체가 막혀 있다
- **4번가 「업카드 페어면 빅벳 선택」** — 7카드 스터드 규칙이다. 라즈에 그대로 적용된다는
  자료가 없다
- **스터드 하이 평가기** — `hi: 'standard'` 인 스터드가 붙을 때
- **`lowest-upcard` · `highest-upcard-by-suit`** — 라즈가 안 쓴다
- **`lib/rush/` · `lib/action-rush/` 를 격자로 옮기는 것** — 전역 금지 사항

## 10. 재미 게이트 (두 칸이 끝나면)

**진행절차**
1. 열린 카드와 엎은 카드가 **한눈에 구분되나?**
2. 「누가 먼저 말하나」를 카드를 보고 고르게 되나, 아니면 찍게 되나?
3. 앤티와 브링인이 블라인드와 다르다는 것이 화면에서 읽히나?

**승자 판독**
1. 제한시간 30초(PLO8 확정값)가 라즈에도 맞나?
2. 스트레이트·플러시가 무시된다는 것을 문제가 **가르치나**, 아니면 그냥 틀리게 만드나?
3. 7장에서 5장을 고르는 일이 4장에서 고르는 것보다 얼마나 더 힘든가?
