# 승자 판독 — 보드보기와 로우 판독을 한 칸으로 합친다

- **날짜**: 2026-09-06
- **상태**: 설계 확정 (사용자 승인 2026-09-06)
- **정본**: [`PRD.md`](../../../PRD.md) §6 (격자) — **이 문서가 §6 을 개정한다**(§7)
- **선행**: [격자 1단계 설계](2026-09-04-grid-plo8-design.md) · 브랜치 `feat/grid-plo8`
- **관련**: [ADR-003](../decisions/ADR-003-gamespec-boundary.md) — `GameSpec` 이 드릴에 무엇을 주는가

---

## 1. 무엇을 바꾸나

**드릴이 일곱에서 여섯이 된다.** `보드보기` 와 `로우 판독` 이 **`승자 판독`** 한 칸으로 합쳐진다.

계기는 사용자가 PLO8 종목 허브를 실제로 보고 낸 판단이다 (2026-09-06).

> 보드보기와 로우 판독은 합쳐야 한다. PLO8 은 로우가 있을 때도 있고 없을 때도 있으니
> 하이 승자와 로우 승자를 함께 골라야 한다.

맞다. **쇼다운에서 딜러가 하는 일은 하나다** — 이 판의 임자를 가리는 것. 하이 게임에서는
그것이 한 사람이고, 스플릿 게임에서는 둘이며, 로우가 성립하지 않으면 다시 한 사람이다.
그것을 드릴 두 개로 갈라 놓으면 **정작 실제로 어려운 자리**(하이와 로우를 동시에 읽고
로우가 없다는 것까지 판단하는 것)를 어느 드릴도 연습시키지 않는다.

## 2. 격자가 어떻게 바뀌나

### 개정된 격자 (PRD §6)

| | 진행절차 | **승자 판독** | 팟리밋 | 팟 분배 | 사고 처리 | 액션 판정 |
|---|---|---|---|---|---|---|
| 노리밋 홀덤 | ⬜ | ✅ | — | ✅ | ⬜ | ✅ |
| PLO | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ | ⬜ |
| **PLO8** | ✅ | ⬜ → **이번** | ⬜ | ⬜ | ⬜ | ⬜ |
| 7카드 스터드 | ⬜ | ⬜ | — | ⬜ | ⬜ | ⬜ |
| 스터드 하이로우 8 | ⬜ | ⬜ | — | ⬜ | ⬜ | ⬜ |
| 라즈 | ⬜ | ⬜ | — | ⬜ | ⬜ | ⬜ |
| 2-7 트리플드로 | ⬜ | ⬜ | — | ⬜ | ⬜ | ⬜ |
| 바두기 | ⬜ | ⬜ | — | ⬜ | ⬜ | ⬜ |

**`—` 열이 하나 사라진다.** 로우 판독은 `eval.lo` 가 없는 종목에서 칸 자체가 없었다.
승자 판독은 **모든 종목에 있다** — 임자를 가리지 않는 포커는 없기 때문이다.

### 스펙이 정하는 것이 한 단계 내려간다

없어진 것은 조건이 아니라 조건이 걸린 **위치**다.

| | 전 | 후 |
|---|---|---|
| `eval.lo === null` 이면 | 로우 판독 **칸이 없다** | 승자 판독이 **로우를 묻지 않는다** |
| `eval.hi === null` 이면 | (해당 없음 — 표현 불가였다) | 승자 판독이 **하이를 묻지 않는다** |

`drillsFor` 가 걷어내던 것을 문제 생성기가 받는다. 종목별로 묻는 것이 이렇게 갈린다.

| `eval` | 종목 | 묻는 것 |
|---|---|---|
| `hi` 만 | 홀덤 · PLO · 7스터드 | 하이 승자 |
| `hi` + `lo` | **PLO8** · 스터드8 | **하이 승자 + 로우 승자** |
| `lo` 만 | 라즈 · 2-7 · 바두기 | 로우 승자 |

**이것이 격자의 다음 시험이다.** 라즈는 PRD §10 5단계이고 `eval.hi` 가 `null` 인 첫 종목이다.
그때 스펙 파일 하나로 로우 전용 화면이 나오면 격자가 맞은 것이고, 화면 코드를 고쳐야 하면
격자가 틀린 것이다. 이번 설계는 **그 판정이 성립할 자리를 미리 만들어 둔다** — 세 갈래를
전부 타입에 적되 구현·검증은 `hi`·`hi+lo` 둘까지다(§6).

### 노리밋 홀덤 칸은 옮기지 않는다

노리밋 홀덤의 승자 판독 칸은 **`/rush`(팟 판독 러시) 를 계속 가리킨다.** 거기 문제 유형
이름이 이미 「승자 판정」이다. 옮기면 449개 테스트가 걸린 코드를 건드리고 얻는 것이 없다
(계획 규칙: `lib/rush/` 를 옮기지 마라).

결과적으로 `/rush` 하나가 승자 판독과 팟 분배 두 칸을 가리킨다. **그것이 지금의 사실이고**,
격자는 사실을 감추지 않는다.

## 3. 문제 하나의 모양

```ts
/** 승자 판독 문제 하나. 정답은 값으로 들어 있지만 그 값을 만든 것은 전부 엔진이다. */
export type WinnerQuestion = {
  seats: WinnerSeat[]        // { name, hole }
  board: Card[]
  buttonSeat: number
  limitSec: number
  /** 이 종목이 무엇을 묻는가. `spec.eval` 이 정한다 — 화면이 정하지 않는다 */
  asks: { hi: boolean; lo: boolean }
  /** 하이 승자 좌석. 동점이면 여럿. `asks.hi` 가 false 면 빈 배열 */
  answerHi: number[]
  /** 로우 승자 좌석. **로우가 성립하지 않으면 빈 배열** — 화면의 「로우 없음」이 이것이다 */
  answerLo: number[]
  /** 채점 후 보여주는 근거 한 줄 */
  why: string
}
```

문제 유형(`kind`)이 **없다.** 기존 로우 판독은 유형이 셋이었다(로우 성립 · 로우 자격 ·
로우 승자). 셋 다 하나로 흡수된다 — 「로우 없음」을 고르는 것이 곧 성립 판단이고,
로우 승자를 고르려면 자격을 먼저 가려야 한다. **사다리를 없앤 것이 아니라 접은 것이다.**

유형이 하나뿐이므로 `RushScreen` 의 `labels: Record<K, string>` 에는 갈래 하나만 들어간다.

### 동점은 그대로 답이 된다

**하이·로우 각각 다중선택이다.** PLO8 에서 로우가 갈리는 쿼터링은 흔하고, 실제 딜러 실수가
가장 많이 나오는 자리다. 단독 승자만 출제하면 **정작 틀리는 것을 연습시키지 않는다.**

### 채점은 이진이다

하이·로우 **둘 다 맞아야 정답이다.** 러시 채점(`useRushRun`)이 정답/오답 둘뿐이라 부분점수를
넣을 자리가 없고, 넣으려면 뼈대를 고쳐야 한다 — 이 드릴 하나 때문에 축 셋이 공유하는 뼈대를
고치지 않는다. 대신 **결과 패널이 하이·로우 어느 쪽이 틀렸는지 갈라서 보여준다.**

### 제한시간

**40초 초안이다.** 기존 로우 승자가 30초였고 하이 판단이 얹힌다. PRD §11 의 열린 질문이고
**재미 게이트에서 확정한다** — 지금 값은 근거가 없는 추정이라는 뜻이다.

## 4. 생성기 — `GameSpec` 빚을 여기서 갚는다

지금 `generateLowRun(seed)` 은 **`GameSpec` 을 아예 받지 않고** `SEAT_COUNT = 4` 와
`QUALIFIER = 8` 을 하드코딩한다. 전체 리뷰가 이렇게 잡아 뒀다.

> `eval.lo` 가 있는 두 번째 종목이 생기는 순간, 그 종목의 로우 판독 화면이 조용히 PLO8
> 문제를 내고 PLO8 최고기록에 쓴다. 컴파일 오류도 실패 테스트도 없다.

어차피 이 파일을 다시 쓰므로 **여기서 청산한다.**

```ts
export function generateWinnerRun(spec: GameSpec, seed: string): WinnerQuestion[]
```

생성기가 스펙에서 읽는 것:

| 스펙 | 쓰는 곳 |
|---|---|
| `eval.hi` · `eval.lo` | `asks` 를 정한다 — 무엇을 물을지 |
| `eval.lo.qualifier` | 로우 자격선. PLO8 은 8, 라즈는 `null` |
| `eval.mustUse` | 2+3 강제 조합인가 아무 다섯 장인가 |
| `holeCardCount` | 좌석당 몇 장을 돌리나 |

정답은 `bestOmahaHi` · `bestOmahaLow` 가 낸다. **드릴 코드에 포커 규칙을 쓰지 않는다.**
좌석 수는 `GameSpec` 에 없다 — 드릴 상수 `SEAT_COUNT = 4` 로 남기되 **`generateWinnerRun`
안에서만 쓴다**(격자 문제가 아니라 이 드릴의 출제 설정이다).

### 출제 조건

판을 하나 돌리고 엔진에게 물어본 뒤, 성립하면 채택하고 아니면 다시 돌린다 —
**먼저 만들고 그다음 보여준다.** 기존 생성기와 같은 방식이다.

**로우는 있어도 되고 없어도 된다 — 없는 것 자체가 답이다.** 그래서 판 하나만 놓고 보면
버릴 이유가 없다(하이 승자는 아무나 다 돌리면 늘 나온다). **성립 조건은 판이 아니라 한 판
열 문제에 걸린다.**

10문제 중 **로우 성립 판 최소 셋, 로우 불성립 판 최소 둘.** 로우가 매번 없으면 「로우 없음」이
정답 고정이 되고, 매번 있으면 아무도 「로우 없음」을 안 누른다. 문제마다 목표를 미리 지정하지
않고 생성기가 남은 목표를 채우는 방식으로 만든다 — 어느 문제가 어느 쪽인지는 시드가 정한다.

**이 배분은 테스트가 지킨다.** 시드 여러 개로 한 판씩 만들어 두 하한이 실제로 지켜지는지
확인한다 — 조건을 주석에만 적으면 생성기가 조용히 어긋난다.

무작위는 `Rng` 로만 얻는다. **생성기 안에서 `Math.random()` 을 한 번이라도 쓰면 시드가
무의미해진다.**

### 화면이 생성기를 고르는 법

`RushScreen` 은 `useMemo(() => generate(seed), [generate, seed])` 로 문제를 만든다.
**렌더마다 새 클로저를 넘기면 매 렌더 새 판이 나온다.** 그래서 `gameId` 당 하나씩
모듈 수준에서 캐시해 함수 정체성을 고정한다.

```ts
// lib/drills/winner/registry.ts
const RUNS = new Map<GameId, (seed: string) => WinnerQuestion[]>()
export function winnerRun(gameId: GameId) { /* 없으면 만들어 캐시 */ }

const RECORDS = new Map<GameId, BestRecord>()
export function winnerRecord(gameId: GameId) { /* 키는 `${gameId}.winner.best` */ }
```

기록 키는 **`plo8.winner.best`** 다. 규약(`<gameId>.<drillId>.best`)을 따른다.
`plo8.lowreading.best` 는 **지우지 않는다** — 기록 키를 지우지 않는 것이 이 레포의 규칙이다.

## 5. 화면

**`RushScreen` 은 한 줄도 고치지 않는다.** props 로 충분하다. 이 뼈대는 지난 단계에서
정반대 형태의 드릴 둘이 무변경으로 공유한 것이고, 이번에도 그래야 한다.

새로 만드는 것은 문제 패널 하나다.

```
┌ 보드 · 좌석 4 (홀카드 4장) ─────────┐
│                                      │
├ 하이 승자는 누구입니까? ─────────────┤
│  [1번] [2번] [3번] [4번]   ← 다중선택 │
├ 로우 승자는 누구입니까? ─────────────┤
│  [1번] [2번] [3번] [4번]   ← 다중선택 │
│  [ 로우 없음 ]                        │
└──────────────────────────────────────┘
                          [ 제출 ]
```

- `asks.lo` 가 false 면 **로우 줄이 아예 그려지지 않는다.** `asks.hi` 도 같다
- 「로우 없음」은 로우 줄의 선택을 비우고 **비운 상태를 명시**하는 토글이다.
  아무것도 안 고른 것과 「로우 없음」을 고른 것을 화면이 구분한다 —
  구분하지 않으면 제출 버튼을 언제 열지 정할 수 없다
- 다중선택 버튼에 `aria-pressed` 를 단다 (지난 리뷰의 Minor 를 여기서 갚는다)
- **360px 에서 좌석 버튼 두 줄이 들어가야 한다.** 홀카드 4장이 좌석을 넘쳤던 결함이
  지난 단계에 실제로 났고 정적 검사로는 안 잡혔다

라우트는 **`/games/[gameId]/winner`** 다. `/games/plo8/low-reading` 은 **삭제한다** —
아직 아무도 링크하지 않았고, 리다이렉트를 남기면 죽은 경로가 영구히 남는다.

## 6. 지금 만들지 않는 것

- **`eval.hi === null`(로우 전용) 갈래**: 타입과 `asks` 는 세 갈래를 다 표현하지만,
  **구현은 라즈가 붙을 때 한다.** 지금 짐작으로 구현하면 검증되지 않은 채 굳는다
  (`firstToAct` 의 미구현 값 넷과 같은 이유)
- **`/rush` 이전** · 팟리밋 계산 · 팟 분배 · 사고 처리 · 딜링 룸 · 새 종목
- **`mustUse` 가 `null` 인 종목**(홀덤·스터드): `bestOmahaHi` 가 2+3 을 강제하므로
  아무 다섯 장 갈래가 필요하지만, **그 종목이 붙을 때 만든다.** PLO8 은 `mustUse` 가 있다
- **공유 보드 5장 하드코딩**: `generateWinnerRun` 의 `dealOnce` 가 공유 보드 5장을 종목에 무관하게
  하드코딩한다. 이 값은 이미 스펙에 있다(§4) — 다음 종목이 붙을 때 스펙에서 읽으면 된다.
  라즈와 스터드는 공유 보드 자체가 없는 게임이므로, 홀덤처럼 평가기만 바꾸는 것과 달리
  **보드 모델 전체를 다시 짜야 한다** — 라즈(§10 5단계)가 붙을 때 이것을 진행한다

## 7. PRD 개정

`PRD.md` 두 곳을 고친다. **PRD 는 사용자 승인 없이 고치지 않는 문서이고, 이 개정은
2026-09-06 사용자 요청에서 나왔다.**

1. **§6 격자표** — 열 일곱을 여섯으로. `보드보기`·`로우 판독` 두 열이 `승자 판독` 한 열로
2. **§6-1 드릴 7종 표** — 6종으로. 승자 판독 행의 「무엇을 묻나」는
   *"이 판의 하이 임자와 로우 임자는 누구인가"*, 정답 출처는 *"하이 평가기 · 로우볼 평가기"*

§6-1 의 「상호작용은 두 형태뿐이다」는 그대로다 — 승자 판독은 여전히 퀴즈다.

## 8. 검증

| | 무엇을 |
|---|---|
| 단위 | 정답이 `bestOmahaHi`·`bestOmahaLow` 와 일치 · 동점 판이 실제로 출제됨 · 로우 없는 판이 최소 둘 · 같은 시드 같은 판 · **NLH 스펙을 넣으면 `asks.lo` 가 false** |
| 타입 | `npx tsc --noEmit` 0 |
| 회귀 | `npx vitest run` 실패 0, **449개 아래로 안 내려감** |
| 빌드 | `npm run build` 성공 |
| 브라우저 | Playwright — `/games/plo8/winner` 가 뜨고 360px 에서 좌석 버튼 두 줄이 안 넘침 |
| **눈** | **실제 브라우저에서 직접 본다.** 지난 단계에 하이드레이션 불일치·안 보이는 글씨가 코드 리뷰 13번을 다 통과하고 브라우저에서 잡혔다 |

## 9. 열린 질문

1. **제한시간 40초** — 근거 없는 초안이다. 재미 게이트에서 사람이 10문제를 해 보고 정한다
2. **로우 성립/불성립 배분 3:2** — 마찬가지로 초안이다. 로우 없는 판이 너무 자주 나오면
   드릴이 싱거워지고, 너무 드물면 「로우 없음」을 아무도 안 고르게 된다
3. **좌석 4** — 기존 로우 판독을 그대로 이었다. 좌석이 늘면 하이·로우 비교가 어려워진다
