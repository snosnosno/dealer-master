## 3. 핵심 결정 — 엔진이 정본이다. 그런데 이번엔 엔진을 고쳐야 한다

축 1 설계는 "**엔진은 동결이다. 한 줄도 고치지 않는다**"였고 그게 맞았다 — 팟 분리·홀칩
순서·핸드 평가는 엔진에 이미 다 있었다.

**축 2 는 다르다.** 러시가 묻는 다섯 중 **둘은 엔진이 답할 수 없다.**

| 유형 | 엔진 상태 |
|---|---|
| 최소 레이즈 총액 | `nlh.minRaiseTo` ✅ (시험 6·7번 회귀 테스트가 증명) |
| 오버사이즈 칩 | `nlh.interpretChipPush` ✅ |
| 다중 칩 베팅 | `nlh.interpretChipPush` ✅ |
| **베팅 기회 재개** | ⚠️ **규정과 어긋난다** — 규정은 누적, 엔진은 단발 |
| **순서 위반** | ⚠️ **개념 자체가 없다** — `grep` 결과 0건 |

여기서 갈림길이 하나 있고, 이 설계는 한쪽을 고른다.

- ~~러시 쪽에 규칙을 새로 쓴다~~ — 정본이 둘이 된다. 축 1 이 홀칩 순서에서 피한 바로 그
  실패다. 그리고 리오픈은 이미 엔진에 **틀린 채로** 있어서, 러시에 옳은 사본을 두면
  같은 규칙이 두 곳에서 서로 다른 답을 낸다
- **엔진을 규정에 맞춘다** ← **이쪽으로 간다**

**결정: 규칙은 엔진에서 고치고, 러시는 그 엔진을 부르기만 한다.**

수정 경계는 좁게 못박는다:

- 손대는 곳은 **`lib/simulator/rulesets/`** 와 그 `BettingContext` 를 만들어 넘기는 호출부뿐
- `reduce.ts` 의 상태 전이 · `pots.ts` · `evaluate.ts` 는 **건드리지 않는다**
- **기존 297 테스트가 그대로 통과해야 한다** (2026-09-01 실측: 23파일 297테스트 통과).
  하나라도 깨지면 그건 규칙 수정이 아니라 회귀다

## 4. 문제 유형 5종

10문제. **유형별 2문제씩 균등**하게 낸다.

> 프로토타입은 "5종 각 1회 + 무작위 5회"였다. 무작위 5회의 기댓값이 유형당 1이므로
> 기대 배분이 곧 2·2·2·2·2 다 — 재미가 확인된 배분을 결정론으로 고정하는 것이지
> 새 배분을 도입하는 것이 아니다.

| 유형 | 개수 | 제한 | 묻는 것 | 입력 | 정답을 내는 엔진 호출 | 조항 |
|---|---|---|---|---|---|---|
| 최소 레이즈 총액 | 2 | 28초 | 다음 사람의 최소 레이즈 **총액** | 숫자 | `nlh.minRaiseTo(ctx)` | 제35조 2항 |
| 다중 칩 베팅 | 2 | 22초 | 선언 없이 민 칩 여러 개는 무엇인가 | 3지 선다 | `nlh.interpretChipPush(ctx, total, 'none', chips)` | 제31조 |
| 베팅 기회 재개 | 2 | 20초 | 이미 액션한 사람이 레이즈할 수 있나 | 2지 선다 | `nlh.canReopen(ctx)` **(신규)** | 제35조 4항 |
| 순서 위반 | 2 | 20초 | 순서를 어긴 액션이 구속력을 갖나 | 2지 선다 | `resolveOutOfTurn(...)` **(신규)** | 제27조 2·3항 |
| 오버사이즈 칩 | 2 | 18초 | 큰 칩 하나를 낸 것은 무엇인가 | 2~3지 선다 | `nlh.interpretChipPush(ctx, chip, declared, [chip])` | 제30조 (+제35조 2항) |

제한시간은 프로토타입 실플레이로 "맞다"가 확인된 값이다. 바꾸지 않는다.

## 5. 엔진 갭 둘 — 무엇이 어떻게 틀렸나

### 5.1 리오픈은 누적인데 엔진은 단발이다 (제35조 4항)

**규정 원문:**

> 한 명 이상의 플레이어가 최소 레이즈 금액에 미치지 못하는 올인을 한 경우, 이미 액션을
> 취했던 플레이어에게 베팅 기회가 다시 돌아왔을 때, **해당 플레이어가 직면한 총 베팅
> 증가액이 유효한 최소 레이즈 금액 이상이 아니라면** 레이즈를 할 수 없다.

**엔진의 현재 판정** (`lib/simulator/generate.ts:151`):

```ts
canRaise: !actedSinceFullRaise.has(seat)
```

즉 "마지막 **풀 레이즈** 이후 내가 액션했나"만 본다. 짧은 올인은 아무리 쌓여도
권리를 되살리지 못한다.

**갈라지는 구체 사례** (BB 2,000):

```
UTG    RAISE 4,700     폭 2,700 (풀)
UTG+1  RAISE 13,500    폭 8,800 (풀)   → 이후 유효 최소 레이즈 폭 8,800
MP     18,000 ALL IN   폭 4,500 (미달) → 폭 갱신 없음
MP+1   23,000 ALL IN   폭 5,000 (미달) → 폭 갱신 없음
```

UTG+1 에게 액션이 돌아왔다.

- **규정**: 직면한 총 증가액 = 23,000 − 13,500 = **9,500** ≥ 8,800 → **레이즈할 수 있다**
- **엔진**: UTG+1 은 마지막 풀 레이즈(자신) 이후 액션했다 → **레이즈할 수 없다** ✗

짧은 올인 둘의 폭이 각각은 미달이지만 **합치면 최소 레이즈를 넘긴다.** 규정은 합을
보고 엔진은 각각을 본다.

**고치는 방법 — 판정을 룰셋 안으로 옮긴다.**

"직면한 총 베팅 증가액"은 새 상태가 필요 없다. 그 좌석이 마지막 액션에서 남긴 벳이
`seatBet` 이므로:

```
직면한 총 증가액 = ctx.currentBet − ctx.seatBet
```

그래서 `BettingContext.canRaise: boolean` (호출부가 계산해 넣어주는 값)을 버리고,
룰셋이 스스로 판정한다:

```ts
// rulesets/nlh.ts
canReopen(ctx) {
  if (!ctx.hasActedThisRound) return true          // 아직 액션 전이면 언제나 권리가 있다
  return ctx.currentBet - ctx.seatBet >= Math.max(ctx.lastRaiseSize, ctx.bigBlind)
}
```

`BettingContext` 는 `canRaise: boolean` → `hasActedThisRound: boolean` 으로 바뀐다.
**규칙이 호출부에서 규칙책으로 이동하는 것**이 이 수정의 핵심이다 — 지금은
`generate.ts` 와 `bots.ts` 가 각자 규칙을 들고 있어, 러시가 세 번째 사본을 만들 판이었다.

`validateAction` 의 `bet`/`raise`/`allin` 분기는 `!ctx.canRaise` 대신
`!this.canReopen(ctx)` 를 본다. 거절 문구(`REOPEN_CLOSED`)도 규정 문구에 맞춘다 —
지금 문구("풀 레이즈에 못 미치는 올인은 베팅을 다시 열지 않습니다")는 단발 해석을
문장으로 굳혀 놓은 것이라, 그대로 두면 화면이 틀린 이유를 가르친다.

### 5.2 순서 위반은 엔진에 아예 없다 (제27조 2·3항)

`outOfTurn` · `순서 위반` · `binding` — `app/src` 전체 검색 결과 **0건**이다.

**규정:**

> 순서를 어긴 액션은, 본래 순서 플레이어의 행동으로 베팅 상황이 변하지 않았다면 구속력을
> 가진다. 본래 순서의 플레이어가 벳 또는 레이즈를 하여 액션이 변경되면, 순서를 어긴
> 플레이어는 자신의 벳을 회수하고 모든 옵션을 새로 가질 수 있다.
> **단, 순서를 어긴 폴드는 언제나 구속력을 가진다.**

순수 함수 하나다:

```ts
resolveOutOfTurn(outOfTurn, proper): { binding: true } | { binding: false; reason: string }
```

**어디에 두나 — `Ruleset` 인터페이스가 아니라 별도 모듈에 둔다.**

`minRaiseTo` · `interpretChipPush` 는 베팅 구조(노리밋/팟리밋/픽스리밋)마다 답이 달라서
룰셋에 있는 게 맞다. 제27조는 **어느 종목에서나 같은 진행 절차**다. `Ruleset` 인터페이스에
얹으면 스터드·드로우·팟리밋 룰셋이 붙을 때마다 동일 구현이 복제되고, 그게 이 레포가
반복해서 막아 온 "정본이 둘" 이다. → `lib/simulator/rulesets/procedure.ts` 신규.

> 반대 의견도 기록해 둔다: "규칙책"이라는 은유를 지키면 제27조도 룰셋에 있어야 한다.
> 복제 위험이 더 크다고 판단해 모듈 분리를 택했다. 뒤집을 이유가 생기면 여기에 적어라.

### 5.3 주석의 거짓말도 함께 고친다

`rulesets/types.ts` 의 `canRaise` 주석은 이렇게 적혀 있다:

> ⚠️ 이 리오픈 규칙에는 조항 번호 근거가 아직 없다 — 계획서·파일럿 문서 어디에도
> 인용이 없다. TDA 2024 PDF 원문으로 조항을 확인할 것.

**근거는 WINNABLE 제35조 4항이다.** 근거가 없던 게 아니라 규칙이 틀렸던 것이다.
`nlh.ts:101` 의 같은 취지 주석도 함께 고친다. 미검증 경고를 남겨 두면 다음 사람이
"아직 확인 안 됨"으로 읽고 또 넘어간다.

## 6. 생성기 — 액션 연쇄를 리듀서에 실제로 통과시킨다

축 1 의 "전원 동점 히든 픽스처"에 해당하는, 이 축의 핵심 기법이다.

문제는 이거다: `minRaiseTo` 와 `canReopen` 은 `BettingContext` 를 받는데, 그 컨텍스트의
`currentBet` · `lastRaiseSize` 를 생성기가 **손으로 계산하면** 짧은 올인이 폭을 갱신하는지
같은 규칙이 생성기에도 생긴다. 그러면 러시가 엔진을 검증하는 게 아니라 자기 사본을
검증한다.

**해법 — 시험 회귀 테스트(`nlh.exam.test.ts`)가 이미 쓰고 있는 방식을 그대로 쓴다.**
좌석을 세우고 `initialState` → `applyEvent` 로 액션을 순서대로 재생한 뒤, **그 결과
상태에서** 컨텍스트를 뽑는다:

```
currentBet    = max(state.seats[].bet)
lastRaiseSize = state.lastRaiseSize     ← 리듀서가 갱신한 값
seatBet       = state.seats[hero].bet
```

생성기는 **얼마를 베팅할지만 고르고**, 그 액션들이 규칙적으로 무엇을 의미하는지는
엔진이 정한다. 프로토타입의 `makeChain` 이 손으로 세던 `lastRaiseSize` 는 앱에 오지 않는다.

### 프로토타입이 알려준 함정 넷

**6.1 오픈 벳은 빅블라인드 이상이어야 한다 (제35조 1항).**
오버사이즈·다중 칩 문제는 **플랍 상황**으로 낸다. 프리플랍이면 빅블라인드가 이미 깔려
있어 "BET"이 성립하지 않고, 칩 액면에서 콜 금액을 거꾸로 만들다 보면 블라인드보다 작은
불법 벳이 나온다. 프로토타입이 실제로 겪은 결함이다.

**6.2 짧은 올인은 반드시 폭에 미달해야 한다.**
`sinc >= lastRaiseSize` 면 그건 풀 레이즈이고 문제의 전제가 무너진다. 생성 후
**엔진의 `isFullRaise` 로 미달을 확인**하고, 아니면 그 판을 버린다 — 생성기가 자기
판단으로 넘어가면 안 된다.

**6.3 선택지 금액이 겹치면 문제가 성립하지 않는다.**
오버사이즈에서 낸 칩이 정확히 최소 레이즈면 "레이즈 (낸 칩)" 과 "레이즈 (최소 레이즈로
채움)" 의 금액이 같아져 두 선택지가 구별되지 않는다. 그 판은 버린다.

**6.4 재개 문제는 두 답이 모두 나와야 한다.**
`canReopen` 이 늘 false 면 "레이즈할 수 없다"만 찍어도 만점이다. 유형별 1,000판 생성에서
**정답 분포가 한쪽으로 90% 이상 쏠리지 않는지** 테스트로 확인한다.

### 공통 규칙

- **무작위는 `createRng(seed)` 하나에서만 나온다.** `Math.random()` 금지 — 시드가 URL 에
  있어야 버그 신고를 받은 판을 다시 열 수 있다 (축 1 과 동일)
- 조건에 안 맞는 판은 `null` 을 돌려 재시도한다. 재시도 상한과 시드 범프는 축 1
  `lib/rush/generate.ts` 구조를 그대로 쓴다 — 무한 루프는 러시에서 가장 나쁜 실패다

| 점수 공식 `(100 + 남은시간×6) × 연속배수` | `lib/rush/score.ts` **그대로 재사용** |
| 음향 (WebAudio 합성) | `lib/rush/sound.ts` **그대로 재사용** |
| 개인 기록 | `lib/rush/record.ts` 를 **키 파라미터화**해서 재사용. 축 2 는 `actionrush.best` |

기록 키는 반드시 분리한다. 두 축은 문제 성격이 달라 점수대가 다르고, 한 키를 공유하면
한쪽 최고점이 다른 쪽을 영원히 덮는다. 프로토타입도 `actionrush.best` 를 썼으므로
**프로토타입에서 세운 기록이 앱으로 이어진다.**

## 8. 화면

프로토타입에서 확정된 것을 옮긴다. 축 1 의 테이블과 **같은 5열 그리드 구조**다
(`components/rush/rush.module.css`) — 이미 두 프로토타입을 이 구조로 통일해 둔 상태다.

- **액션 로그가 테이블 위에 있다.** 최소 레이즈·재개 유형은 로그를 읽어야 풀린다
- **좌석에 액션 라벨과 칩을 함께 보여준다.** 순서 위반은 "C가 B를 건너뛰었다"가
  좌석 순서로 보여야 문제가 성립한다 — 목록으로는 드러나지 않는다
- **hero 좌석을 강조한다.** 누구에 대한 질문인지가 지문에만 있으면 매번 다시 읽는다
- **채점 후 조항 패널.** 조항 번호 + 원문을 그대로 인용한다. 이게 축 2 의 학습 가치다
- 카드는 그리지 않는다. 이 다섯 유형은 홀카드·보드와 무관하다

### 딜러 버튼은 그리지 않는다 (그리고 그게 의도다)

프로토타입 주석이 근거를 남겨 놓았다:

> 좌석 배열이 SB 부터 시작하므로 버튼은 배열 밖(SB 직전)에 있고, 이 유형들의 정답은
> 버튼 위치와 무관하다. **자리를 지어내 표시하면 틀린 것을 가르치게 된다.**

축 1 은 반대로 "버튼을 모든 유형에 표시"했는데, 거기선 홀칩 문제의 정답이 버튼에
달려 있어 감추면 유형이 새어나갔기 때문이다. **두 축의 결론이 다른 이유는 정답이 버튼에
의존하느냐다.** 데드 버튼 유형을 만들 때 좌석 모델을 확장하고 이 결정을 다시 본다.

## 13. 이 설계가 지키는 것

**"정답을 반드시 엔진이 낸다."** 축 1 에서는 그게 "엔진을 고치지 않는다"로 나타났고,
축 2 에서는 **"엔진을 규정에 맞게 고친다"** 로 나타난다. 표면은 반대지만 원칙은 하나다 —
규칙은 한 곳에만 있어야 하고, 그곳은 엔진이다.

러시 쪽에 규칙을 한 줄이라도 쓰고 싶어지면 그건 엔진이 부족한 것이지 러시가 특별한
것이 아니다. 그때는 엔진을 고쳐라.
