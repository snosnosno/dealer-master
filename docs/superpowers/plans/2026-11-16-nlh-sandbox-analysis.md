# 노리밋 홀덤 샌드박스 — 상세 분석

- **날짜**: 2026-11-16
- **상태**: §8 결정 확정 (2026-11-16). 프로토타입 1판이 섰다 (§9). **다음은 사람이 하는 재미 게이트다**
- **선행**: [PRD.md](../../../PRD.md) §6-2 · §10 · [ADR-002](../decisions/ADR-002-run-mode-dropped.md) ·
  [축 3 방식 다섯 가지](2026-09-02-axis3-simulation-options.md) · [DealerSim 해부](../reviews/2026-08-30-dealersim-teardown.md)
- **질문**: "지금 것을 기반으로 2D 샌드박스 시뮬레이션 게임을 만들면 어떤가. 홀덤으로 먼저."

---

## 0. 결론 먼저

**만들 만하다. 단, 지금까지 세 번 실패한 형태를 네 번째로 만들면 안 된다.**

"딜러가 화면에서 핸드를 진행하는 게임"은 이 레포에서 이미 세 번 시도됐다(§1).
세 번 다 같은 벽에 부딪혔다 — **반복되는 의식(儀式)은 세 판이면 외워지고, 외운 뒤에는 할 일이 없다.**

홀덤 샌드박스가 앞의 셋과 달라질 수 있는 근거는 둘이고, 둘 다 홀덤에만 있다.

1. **핸드가 이어진다.** 지금까지 모든 프로토타입과 드릴은 핸드마다 새 테이블이었다.
   샌드박스는 스택·버튼·좌석이 다음 핸드로 넘어간다. 그러면 **누가 탈락했는지·누가 새로 앉았는지에
   따라 버튼과 블라인드의 답이 매번 달라진다.** 드릴에서는 버튼 이동이 "한 칸 옆"이라 자명했지만,
   이어지는 테이블에서는 실제 TD 판정이 된다. 이건 핸드를 이어 붙여야만 생기는 판정이다.
2. **홀덤의 사고 자료가 이미 있다.** 축 3 은 플랍게임 사고를 "자료 없음"으로 비워 뒀다
   (`mix-room.html` `mkIncident` 가 `family: 'flop'` 에서 `null`). 그런데 홀덤은 TDA 케이스
   30 건(`05`·`11_pilot_cases`)과 액션 판정 5 조항(`lib/action-rush/articles.ts`)이 이미 쓰여 있다.
   그중 여럿이 **"실질 액션(SA) 전이냐 후냐"로 답이 뒤집히는 구조**다 — 축 3 이 사고를
   "목록이 아니라 조합"으로 만들 수 있었던 바로 그 구조다.

그래서 권하는 형태는 이렇다.

> **카드·칩 같은 의식은 자동으로 흘러가고, 판정은 이어지는 테이블에서 연달아 터지고, 테이블 상태는 쌓인다.**

이건 PRD §6-2 의 **딜링 룸**에 "핸드 이월"을 더한 것이다. 새 개념이 아니라 PRD 가 이미
예약해 둔 자리다. 그리고 그 자리를 채우는 데 필요한 홀덤의 빈 칸 둘(진행절차 · 사고 처리)이
그대로 격자의 빈 칸이다(§4).

## 1. 지금까지의 시도 — 같은 벽에 세 번

| 시도 | 형태 | 결과 | 남긴 교훈 |
|---|---|---|---|
| **C 모드** (홀덤, 2026-08-30) | 학습자가 16 스텝을 클릭해 핸드를 진행 | **폐기** (ADR-002) | 16 스텝 중 진짜 판단은 6 개. 나머지 10 개는 순서만 알면 맞는 클릭이고, 순서는 세 판이면 외워진다 |
| **mix-deal** (축 3) | 진행 + 팟리밋 계산 | 게이트 미통과 | "할 일이 없었다 + 긴장이 없었다" |
| **mix-room 딜링 룸** (축 3) | 자동 딜 + 사고·항의 + 생명 3 | 게이트에서 **강등** | "딜링룸보다는 연습 위주로". 지루한 유형 = 매 판 반복되는 좌석 지목·벳 크기 |
| **진행절차 드릴** (앱) | 팔레트에서 다음 행동을 스스로 고름 | **살아남음** → PLO8 · 라즈 | 사용자가 처음부터 원한 형태. 생명·시간 없이 손에 순서를 붙인다 |

두 가지가 겹쳐 보인다.

- **사용자는 계속 "실감"을 원한다.** 2026-09-02 답변: "실제 딜링 절차를 배우면서 시뮬레이션도 하고
  실감나게 게임하는 것처럼 하고 싶다." 샌드박스 제안도 같은 요구다.
- **실감을 의식(클릭)으로 채우면 반드시 소진된다.** ADR-002 의 결론이고, DealerSim 이 20 년 동안
  보여 준 결론이다.

**따라서 실감은 눈(애니메이션)으로 주고, 손은 판정에만 쓴다.** 축 3 에서 이미 확정한 원칙
("카드 배분은 자동, 판단만 손으로, 단 카드가 실제로 이동하는 애니메이션")을 그대로 가져온다.

축 3 문서 §6 의 경고도 유효하다 — **"세 번째 실패는 방식의 실패로 기록한다. 같은 방식을 네 번
시도하지 않는다."** 홀덤 샌드박스는 §0 의 두 근거가 실제로 작동하는지를 확인하는 실험이어야 하고,
mix-room 의 홀덤 판본이어서는 안 된다.

## 2. 샌드박스의 한 바퀴

### 세 층

| 층 | 무엇이 있나 | 누가 움직이나 |
|---|---|---|
| **자동층** | 셔플 · 홀카드 딜 · 번 · 보드 · 봇 액션 · 칩 수거 · 미콜 반환 | 엔진. 애니메이션 카드 한 장 0.15 초, 아무 때나 건너뛰기 (축 3 확정값) |
| **판정층** | 아래 표 | **사용자의 손.** "무엇을"은 고르고, "누구에게·어디에"는 테이블을 직접 클릭 (축 3 확정값) |
| **누적층** | 좌석별 스택 · 버튼 위치 · 탈락 · 새 착석 · 블라인드 레벨 · 핸드 번호 | 핸드가 끝날 때마다 다음 핸드로 넘어간다 |

### 판정층 — 무엇이 언제 터지나

| 판정 | 언제 | 답이 매번 다른 이유 | 정답의 출처 |
|---|---|---|---|
| **버튼·블라인드 위치** | 다음 핸드 시작 전. **탈락·새 착석이 있었을 때만** 묻는다 | 누가 빠졌는지에 따라 데드 버튼, 블라인드를 누가 내는지가 갈린다. 헤즈업이 되면 규칙이 바뀐다(케이스 12) | **새로 만든다** — 세션 층 (§4) |
| **팟 지급** | 쇼다운. 올인이 겹쳤을 때 사이드팟 | 스택이 이월되므로 올인 구도가 자연스럽게 생긴다 | `buildPots` · `awardPots` (있음) |
| **승자 판독** | 쇼다운 | 보드마다 다르다 | `evaluateHand` (있음) |
| **액션 판정** | 봇이 애매한 액션을 했을 때 | 오버사이즈 칩 · 다중 칩 · 순서 위반 · 최소 레이즈 · 리오픈 | `nlh` 룰셋 · `action-rush` 문제 6 종 (있음) |
| **사고 수습** | 아무 때나, 핸드당 0~2 건 | 같은 사고라도 **SA 전후 · 스트릿 · 대상**으로 답이 갈린다 | 케이스 30 건에서 추린다 (**원문 대조 필요**, §5) |
| **항의** | 핸드당 많아야 1 건 | 사실인 항의와 거짓인 항의가 섞인다 | mix-room `OBJ` 구조를 홀덤 내용으로 채운다 |

**원칙 하나 — 판단이 자명하면 묻지 않는다.** mix-room 이 지루해진 이유가 매 판 같은 걸 물은
것이었다. 탈락이 없는데 버튼을 묻지 않고, 사이드팟이 없는데 팟 분리를 묻지 않는다.
샌드박스의 질문 수는 **테이블 상태가 정한다.** 이게 드릴과 샌드박스가 갈리는 지점이다.

### 홀덤 사고 후보 — 이미 쓰인 케이스에서

"SA 전/후" 같은 갈림길이 있는 것을 먼저 고른다. 갈림길이 없는 사고는 한 번 보면 외워진다.

| 사고 | 갈림길 | 근거 케이스 |
|---|---|---|
| 버튼 위치 오류 발견 | SA 전 → 정정 / SA 후 → 그대로 진행, 다음 핸드에 정상 이동 | 케이스 5 (Rule 34-A) |
| 카드 장수 오류 | SA 전 → 미스딜 / SA 후 → 그 좌석만 데드, 번은 정상 1 장 | 케이스 6 (Rule 35-D · 36 · 38) |
| 순서 위반 액션 | 건너뛴 사람이 체크했나, SA 가 됐나 | 케이스 8 (Rule 53-B) · `outofturn.ts` |
| 딜 시점 자리 비움 | 마지막 카드가 돌 때 자리에 있었나 | 케이스 11 (Rule 30) |
| 카드가 모자란 걸 알고 액션 | 알고 액션했나, 즉시 말했나 | 케이스 13 (Rule 37) |
| 최소 레이즈 미달 | 다음 스트릿 딜 전인가 후인가 | 케이스 19 (Rule 52-A) |
| 올인 쇼다운 카드 공개 | 베팅이 끝났나 | 케이스 1 (Rule 16) |
| 숨은 칩 발견 | TD 재량 — 정답이 아니라 기본값 | 케이스 26 (Rule 62) |

여덟 개 중 최소 여섯은 두 갈래다. **첫 프로토타입은 이 중 두 갈래짜리 셋이면 충분하다**
(축 3 문서 §4 의 기준과 같다). 1 순위 후보: 버튼 위치 오류 · 카드 장수 오류 · 최소 레이즈 미달.
셋 다 "언제 발견했나"가 답을 뒤집는다.

## 3. 이미 있는 것 — 재사용 지도

**판정의 정답은 대부분 이미 엔진에 있다.** 새로 만들 것은 핸드를 이어 붙이는 층과 사고 발생기다.

| 필요한 것 | 있는 곳 | 상태 |
|---|---|---|
| 이벤트 기반 핸드 진행 (되감기·시드 재현) | `lib/simulator/reduce.ts` · `types.ts` (`HandEvent`) | ✅ 그대로 |
| 봇 액션 | `lib/simulator/bots.ts` `decideAction` | ✅ 그대로 |
| 노리밋 판정 (최소·최대 레이즈, 리오픈, 칩 해석) | `lib/simulator/rulesets/nlh.ts` | ✅ 그대로 |
| 사이드팟 · 홀칩 · 지급 | `lib/simulator/pots.ts` | ✅ 그대로 |
| 하이 평가기 | `lib/simulator/evaluate.ts` | ✅ 그대로 |
| 진행 스텝 · 첫 액션 좌석 | `lib/drills/procedure/` — **`GameSpec` 만 읽는다** | ✅ 홀덤 스펙으로 돌 것으로 보인다. 라우트가 없을 뿐 (§4) |
| 액션 판정 문제 6 종 | `lib/action-rush/questions/` | ✅ 사고·항의 소재로 |
| 조항 원문 5 개 | `lib/action-rush/articles.ts` (WINNABLE 제27·30·31·35 조) | ✅ |
| 테이블 화면 · 좌석 · 재생 | `components/table/PokerTable.tsx` · `Seat.tsx` · `simulator/HandPlayer.tsx` | ✅ 2D 테이블은 이미 있다 |
| 카드가 날아가는 애니메이션 · 항의 구조 | `prototypes/mix-room.html` (`flyTo`, `OBJ`) | ✅ 프로토타입에서 그대로 |
| **핸드 이월** (스택 · 버튼 · 탈락 · 착석) | — | ❌ `generateHand` 는 핸드마다 스택을 새로 뽑고(`pickStacks`) 시작 상태를 받지 않는다 |
| **홀덤 사고 발생기** | — | ❌ 축 3 의 `INC` 는 스터드·드로우뿐이다 |
| **버튼 이동 규칙** (데드 버튼 · 미스드 블라인드) | — | ❌ 레포에 조항이 없다. 원문 확인 필요 |

## 4. 새로 만들 것 — 그리고 그게 격자와 겹친다는 점

### (1) 세션 층 — `TableSession`

핸드 하나를 넘어서는 상태. 이벤트 리듀서 패턴을 한 층 위로 올린다.

```
TableSession = {
  seats: { name, stack, status: 'active' | 'busted' | 'away' | 'new' }[]
  buttonSeat, level: { sb, bb, ante }, handNo,
  missedBlinds?: ...      // 캐시게임을 할 때만
}
nextHand(session, seed) → Hand        // generateHand 가 시작 상태를 받도록 넓힌다
afterHand(session, finalState) → session
```

- `generateHand` 에 `seats`·`buttonSeat` 를 **밖에서 넣는** 경로가 필요하다. 지금은 안에서 정한다
- 버튼 이동은 **판정 메서드다** — 룰셋처럼 정답을 내는 곳이 하나여야 한다(ADR-003 의 원칙).
  화면이나 생성기에 사본을 두면 갈라진다
- 시드 결정론을 지킨다 — 세션 시드 + 핸드 번호로 핸드 시드를 만든다

### (2) 사고 발생기 — 플랍 패밀리판

`{ 종류, 시점(SA 전/후 · 스트릿), 대상 좌석 }` 조합에서 뽑는다. 축 3 문서 §4 의 규칙을 그대로 지킨다.

1. 발생기로 만든다. 고정 목록은 안 된다
2. 두 갈래 이상인 사고를 셋 이상
3. **원문에 근거가 있는 것만.** 없으면 뺀다

### 격자와 겹친다

홀덤 줄의 빈 칸은 **진행절차**와 **사고 처리** 둘이다(`lib/games/routes.ts`).
샌드박스의 자동층이 진행절차이고, 판정층의 중심이 사고 처리다. 즉

```
홀덤 진행절차 칸  ──┐
홀덤 사고 처리 칸 ──┼──▶ 홀덤 딜링 룸 (+ 핸드 이월) = 샌드박스
기존 3 칸        ──┘
```

**샌드박스를 만들면서 홀덤 줄이 다 찬다.** PRD 의 "한 종목의 칸이 전부 차고"에 그대로 맞는다.
그리고 **샌드박스가 재미 게이트를 못 넘어도 사고 발생기는 남는다** — 사고 처리 드릴(퀴즈)로
격자의 칸이 된다. 실패해도 버려지는 코드가 적다.

진행절차 칸은 거의 공짜일 수 있다. 진행절차 드릴은 `spec.forced`·`spec.streets` 만 읽고,
`forced: 'blinds'` 경로는 PLO8 이 이미 쓴다. 홀덤에 열려면 `routes.ts` 에 한 줄과 테스트가 필요해
보인다. **이것 자체가 "다음 종목이 스펙 파일 하나로 붙는가"의 판정이다** — 확인할 가치가 있다.

## 5. 위험

| 위험 | 크기 | 대응 |
|---|---|---|
| **네 번째 의식 게임이 된다** | 큼 | §2 원칙 — 자명한 판단은 묻지 않는다. 게이트에서 "결국 보기 고르기더라"가 나오면 멈춘다(§7) |
| **사고 정답의 근거** | 큼 | 케이스 30 건은 2026-08 초안이고 TDA 조항 번호로 적혀 있다. 조항 정본은 WINNABLE 제60조까지이고(`references/README.md`), ADR-002 가 미확인 8 종을 따로 적어 뒀다. **원문은 로컬 `참고문서/` 에만 있어 이 환경에서 대조할 수 없다** — 프로토타입에 넣을 사고 셋과 데드 버튼 규칙은 사용자가 원문으로 확인해야 한다 |
| **사용자가 이미 "연습 위주"를 골랐다** | 중 | 생명 3 을 기본값으로 두지 않는다. 기본은 끝없는 연습 테이블, 시험(생명)은 선택지로 둔다. mix-room 의 순서를 그대로 따른다 |
| **한 핸드가 길다** | 중 | 봇 액션 빨리 감기(축 3 확정). 목표: 판정 하나에 30 초 이상 기다리지 않는다 |
| **9 인 테이블이 모바일에 안 들어간다** | 중 | 엔진은 9 인까지 된다(`MAX_SEATS = 9`). 좌석 넘침 e2e 가 이미 있다. 프로토타입은 6 인으로 시작한다 |
| **PRD 순서와 충돌** | 작음 | PRD §10 은 라즈 게이트 → 종목 확장이 먼저다. 다만 홀덤 샌드박스는 홀덤 줄을 채우는 일이라 격자 방향과 같다. **라즈 재미 게이트(사람이 할 일)는 여전히 먼저다** |

### 3D 를 빼는 이유 (다시 확인)

손이 판정에만 쓰이는 게임이라 카메라를 돌릴 일이 없다. 3D 가 주는 몰입은 판정의 질을 올리지
않고, 카드·칩이 가려지는 각도가 생기고, 모바일 웹이 무거워진다. **2D 테이블 + DOM/CSS 애니메이션**
(mix-room 의 `flyTo` 방식)으로 충분하다. PRD §10 6 단계가 말한 "필요하면 캔버스"도 아직 필요 없다.

## 6. 순서 제안

```
0. 사용자 결정 (§8) + 사고 셋 · 데드 버튼 규칙 원문 확인       ← 사람
1. 단일 HTML 프로토타입 — prototypes/nlh-table.html                ← 프로토타입 우선 원칙 (PRD §10)
   · 6 인, 토너먼트, 핸드 이월(스택 · 버튼 · 탈락)

   · 기본은 연습 테이블, 시험 모드는 선택
   (병행 가능) 홀덤 진행절차 칸 열기 — routes.ts 한 줄 + 테스트
2. 재미 게이트 (§3 3 문항) — 사람이 한 세션을 끝까지
3. 통과하면 앱 이식
   · lib/session/ (TableSession) · generateHand 시작 상태 받기

   · /games/nlh/table
```

1 단계는 하루 이틀 분량이다. 프로토타입은 `Math.random()` 을 써도 된다 — 시드 결정론은
앱 이식 때 지킨다.

## 7. 이 분석이 틀렸다고 판명되는 지점

- **게이트에서 "핸드가 이어져도 결국 매번 같은 걸 묻는다"** → §0 의 근거 1 이 죽은 것이다.
  탈락·착석이 판정을 충분히 자주 만들지 못한다는 뜻이다
- **"사고가 터져도 결국 보기 고르기다"** → 축 3 문서 §6 과 같은 실패다. 문제는 입력의 물리성이고,
  샌드박스를 더 키우지 말고 사고 발생기를 퀴즈 드릴로 내린다
- 둘 중 하나라도 나오면 **방식의 실패로 기록하고, 홀덤 진행 게임을 다섯 번째로 만들지 않는다.**

## 9. 프로토타입 1판 (2026-11-16)

§8 의 답: **토너먼트 · 바로 채점 + 핸드 끝 요약 · 기본은 연습 테이블(시험은 선택) · 6 인 ·
첫 사고 셋은 버튼 위치 오류 / 카드 장수 오류 / 최소 레이즈 미달.**

파일: `docs/superpowers/prototypes/nlh-table.html` · `localStorage` 키는 `nlhtable.best` (시험 최고 기록)

### 들어간 것

| 층 | 내용 |
|---|---|
| 자동층 | 블라인드 · 홀카드(카드가 덱에서 날아간다, 「건너뛰기」로 끈다) · 번 · 보드 · 봇 액션 · 미콜 반환 · 칩 수거 · 올인 런아웃 |
| 판정층 | 사고 3 종(각각 두 갈래) · 쇼다운 팟마다 임자 지목(사이드팟 따로, 동점은 여럿) · 탈락·착석 뒤 버튼/SB/BB 를 테이블에서 직접 놓기 |
| 누적층 | 스택 이월 · 탈락하면 자리가 빈다 · 3 명 이하면 다른 테이블에서 착석 · 5 핸드마다 블라인드 상승 · 데드 버튼 / 데드 스몰 |

**자명하면 묻지 않는다** — 버튼은 탈락이나 착석이 있었던 핸드 뒤에만 묻고, 다툴 사람이 한 명인 팟은 묻지 않는다.

### 사고의 두 갈래

| 사고 | 갈래를 가르는 것 | 정답 |
|---|---|---|
| 버튼 위치 오류 | 발견 시점까지 실질 액션(SA)이 성립했나 | 전 → 미스딜, 바른 위치로 다시 딜 · 후 → 그대로 진행, 다음 핸드에 바로잡는다 |
| 카드 장수 오류 (1 장 / 3 장) | 같음 | 전 → 미스딜 · 후 → 그 좌석만 데드, 이미 낸 칩은 팟에 남는다 |
| 최소 레이즈 미달 ("레이즈" 선언 후 모자란 금액) | 다음 스트릿이 깔렸나 | 전 → 최소 레이즈까지 채운다 · 후 → 그대로 선다 |

SA 판정은 블라인드를 빼고 프리플랍 액션으로 한다 — 액션이 셋이거나, 둘 중 하나라도 칩이 들어갔으면 SA.
발견 시점(액션 0~3 개 뒤)을 무작위로 뽑으므로 **로그를 읽어 SA 를 스스로 세야** 답이 나온다.

### 일부러 뺀 것 — 원문 확인 전이라 출제하지 않는다

- **새 손님이 버튼~SB · SB~BB 사이에 앉는 경우.** 그 자리는 피해서 앉힌다. 안전한 자리가 모자라
  네 명을 못 채우면 **테이블 재편**(빈 자리를 다 채우고 버튼 재추첨)으로 넘긴다 — 그 핸드는 버튼을 묻지 않는다
- **헤즈업 전환 규칙.** 4 명 미만이 되지 않게 해서 생기지 않는다

### 자동 점검 (Playwright, 무작위로 답하며 150 핸드 × 여러 번)

- 콘솔 오류 0 · **칩 보존 위반 0** (핸드마다 총액 = 직전 총액 + 새 손님 스택)
- 150 핸드에 판정 약 300 개 — 핸드당 2 개쯤. 버튼 판정 40 여 회, 사고 셋과 두 갈래가 모두 나온다
- 데스크톱 1100px · 모바일 390px 스크린샷으로 배치 확인

### 정답 근거 — 확인이 필요한 것

채점 화면의 근거에 전부 「원문 확인 전」이 붙어 있다. 사용자가 원문(TDA 2024 · WINNABLE)으로 볼 것:

1. **데드 버튼 규칙** — BB 는 반드시 한 칸 앞으로, SB 는 지난 BB 자리(탈락이면 없음), 버튼은 지난 SB 자리(비었으면 빈 자리)
2. **버튼 오류가 SA 뒤에 발견됐을 때 다음 핸드** — 프로토타입은 "원래 있어야 할 위치에서 정상 이동"으로 처리했다.
   케이스 5 의 「다음 핸드에서는 정상적으로 이동」이 이 뜻인지 확인할 것
3. **카드 장수 오류 · SA 뒤** — 케이스 6 은 「그 좌석만 먹」이다. 카드가 **모자란** 경우와 **남는** 경우가 같은 처리인지
4. **최소 레이즈 미달** — 「레이즈」를 선언했을 때 최소 금액까지 채우게 하는 것이 맞는지(콜로 되돌리는 경우와 구분)
5. **SA 정의** — 블라인드를 세지 않는다는 것

### 재미 게이트 — 사람이 한 세션을 끝까지

PRD §3 의 세 문항에 이 프로토타입 고유의 질문을 붙인다.

1. **다시 하기가 눌리나?** — 연습 테이블을 20 핸드쯤 돌린 뒤 그만두고 싶은가, 더 하고 싶은가
2. **지루한 유형이 있나?** — 특히 **팟 임자 지목**. 매 쇼다운마다 나오는데 mix-room 의 좌석 지목처럼 지루해지는가
3. **시간이 맞나?** — 봇 액션 0.42 초 간격과 카드 애니메이션
4. **핸드가 이어지는 게 느껴지나?** — §0 근거 1. 탈락 뒤 버튼을 놓을 때 "앞 핸드를 기억해야 풀린다"는 감각이 오는가, 아니면 그냥 또 하나의 퀴즈인가
5. **SA 를 세는 게 판정으로 느껴지나?** — §0 근거 2. 로그를 읽고 세는 것이 재미인가 귀찮음인가

4·5 중 하나라도 "아니다"면 §7 의 실패 지점에 해당한다.
