### 근거 — 창 N = 20

`action_validity` 부재율 0.327(300시드 실측 98건) 기준 계산:

| N | 창 전체 결측 확률 | 표본 1개 이하 확률 | 기대 표본수 |
|---|---|---|---|
| 3 | 3.50% | 25.1% | 2.0 |
| 5 | 0.37% | 4.2% | 3.4 |
| 10 | 0.0014% | 0.03% | 6.7 |
| **20** | **1.6e-10** | **사실상 0** | **13.5** |

즉 백로그가 원래 걱정하던 두 결함(미측정 축이 0 으로 평균 / 최소표본 없음)은 **좁은 창에서만**
실제 위험이고 N=20 에서는 확률적으로 무력화된다. 코드가 방어하지는 않으므로 주석에 남겼다.

> 원장 표현 정정: "창 안에서 한 번도 측정 안 된 축이 0 으로 평균된다"는 서술은 **부분적으로
> 과장이었다.** `gradeFrom` 의 `avg` 는 `null` 을 걸러내므로(`score.ts`) 일부 미측정은 이미
> 올바르게 처리된다. 0 이 되는 것은 창 **전체**가 결측일 때뿐이고, 그 확률이 위 표다.

### 근거 — 나머지

- **#3**: 런타임 산술은 원래부터 옳았다(`null !== f.answer` 로 오답). 막고 있던 것은 **타입뿐**이라
  전환 비용이 타입 한 줄이었다. UI 배선 전인 지금이 가장 쌌다 — 나중이면 저장된 답안까지 마이그레이션.
- **#4**: `gradeFrom` 반환값을 senior 로 누르지 **않았다.** 누르면 3단계가 조건을 마저 배선할 때
  되돌릴 자리를 잃고 지금 초록인 문턱 테스트도 의미를 잃는다. 소비하는 쪽이 최고 표시 등급을 정한다.
- **#5**: R40 이 번호를 뺀 두 근거 중 ①("확인 못 한 번호는 안 쓴다")이 원문 대조로 해소됐고,
  ②("근거는 사이드팟 배분이 아니라 족보 판정")는 그대로 유효한데 Rule 12 가 바로 그 족보 판정
  조항이라 오히려 정확히 맞는다.
- **#9**: 금액만으로 통일했다. 오답 후보의 `why` 는 코드에 남겼다 — 어떤 착각을 재현한 금액인지가
  후보 설계의 근거이고, 지우면 다음 사람이 임의의 숫자를 넣는다.

### 결정 불필요 — 인지 사항

- **`junior` 는 조건이 아니라 폴백 (R32)** — 스펙은 "절차 축 80% 이상"이라는 조건이지만 코드는
  조건 없는 폴백이라 절차 30% 학습자도 junior 가 된다. 주석에 정직하게 기록돼 있고 동작은
  의도적으로 안 건드렸다. **"junior 도 자격"으로 쓸 거면 그때 결정 항목으로 올라온다.**
- **`difficulty` 는 무효과**, **`rulesetId` 는 룰셋을 고르지 않는다**(값이 하나뿐). 둘 다 의도된
  것이고 선언부에 문서화돼 있다(R24). **UI 에 노출하지 말 것.**
- **Task 7 #6** — `require:['calculation']` 시드는 사이드팟을 만들려 올인을 강제하므로 플레이가
  비현실적이다. 딜러 훈련에는 무해하지만(딜러는 플레이 질을 판정하지 않는다) **"이 플레이어의
  선택이 옳았나" 류 콘텐츠를 이 시드 위에 짓지 말 것.**

### 2단계 브리프에 반드시 실을 것 (#2 의 산출물)

1. `require` 4종 중 **`action_validity` 만 최선 노력이다** — 약 32.7% 핸드에서 안 나온다.
   나온 판단 지점을 확인하고 없을 때의 처리를 UI 가 정해야 한다. 재시도 루프는 금지다.
2. `difficulty` 무효과 · `rulesetId` 단일값 — 컨트롤로 노출하지 말 것.
3. 최고 표시 등급은 **senior** (master 는 3단계 이상감지 배선 후).
4. 판단 지점 개수는 핸드마다 다르고 **0개도 가능**하다.
5. 좌석 번호가 두 벌이다 — API 는 0-based, 학습자 문구는 1-based.

## G. 프로세스 관찰 — 다음 계획에 넘길 것

최종 리뷰가 반대한 판정 4건 중 3건이 같은 모양이다: **태스크 N 에서 내린 판정이 태스크 N+k 가
구현할 동작에 대한 것인데, 착지한 코드에 대고 재검증된 적이 없다.** R22 가 가장 명확한 사례
(전제는 "핸드 내용"에 관한 것인데 `require` 는 "판단 지점"에 대한 약속 — 32.7% 미이행).

값싼 가드: **"X 는 구조적으로 보장된다"고 주장하는 판정은 같은 fix 라운드 안에서
그 X 를 *소비하는 층*에서 단언하는 테스트로 변환한다** — 입력을 *생산하는* 층이 아니라.

이 브랜치는 구조적으로 실패 불가능한 테스트를 4건 출하했고 전부 리뷰에서 잡혔다.
"어떤 구현 변경이 이 단언을 실패시키나"를 매번 묻게 한 것이 그것을 잡았다.
