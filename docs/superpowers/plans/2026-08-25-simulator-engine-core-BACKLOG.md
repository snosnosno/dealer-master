## C. 2단계(UI) 착수 전에 정해야 하는 설계 결정

- **등급 이동평균 창 N** — 스펙·계획서 모두 미결정으로 명시 연기. R47 의 32.7% 를 전제로 정할 것.
  `gradeFrom` 은 최소표본 규칙이 없어서, 창 안에서 한 번도 측정 안 된 축이 0 으로 평균되고
  한 번 측정된 축이 스무 번 측정된 축과 같은 무게를 갖는다. **Task 9 M4 와 함께 결정할 것**
  (`score.ts:79-81` 이 빈 결과집합에 0 을 반환 — "전부 틀림"과 구분 불가).
- **`require` 정직성 (R39/C1)** — `'calculation'`·`'showdown'`·`'procedure'` 는 경성 보장이지만
  **`'action_validity'` 는 최선 노력이다** (300시드 중 98건 미이행 = 32.7%). 2단계 UI 작성자가
  엔진이 하지 않는 약속 위에 짓지 않도록 브리프에 명시할 것.
- **`Answer.values: number[]` 의 중간 빈 칸** — 꼬리 빈 칸은 표현되지만(R31, 짧은 배열=감점)
  "1번 칸만 비우고 2번 칸 입력"은 표현할 수 없다. UI 가 0 으로 메꾸거나 배열을 당기면 채점이
  왜곡된다. `(number|null)[]` 전환 여부가 UI 배선 시점의 결정.
- **`master` 등급의 미구현 절반 (R30)** — 스펙 L255 는 "3축 90% + **B 모드 이상 검출률 70%**"
  인데 `score.ts:84` 는 앞 절반만 본다. 이상감지 모드가 3단계라 지금 구현 불가. 두면 이상 검출을
  한 번도 시험받지 않은 학습자가 master 로 인증된다. `score.ts:115-118` 과 계획서 미결정 표에 기록됨.
- **`junior` 는 조건이 아니라 폴백 (R32)** — 스펙 253 은 "절차 축 80% 이상"이라는 조건이지만
  코드는 조건 없는 폴백이라 절차 30% 학습자도 junior 가 된다. `score.ts:108-111` 에 정직하게
  문서화돼 있고 동작은 의도적으로 안 건드렸다.
- **`difficulty` 는 현재 무효과**, **`rulesetId` 는 룰셋을 고르지 않는다**(값이 하나뿐).
  둘 다 의도된 것이고 선언부에 문서화돼 있다(R24).
- **Task 7 #6** — `require:['calculation']` 시드는 플레이가 비현실적이다. 그 시드 위에
  플레이어 판단(play-quality) 콘텐츠를 짓지 말 것. 딜러는 플레이 질을 판정하지 않으므로
  범위상 옳지만, 2단계가 모르면 오용한다.
- **쇼다운 문항에 `Rule 12` 를 붙일지 (신규, 2026-08-29)** — R40 이 번호를 뺀 이유는 "확인 못 한 번호는
  안 쓴다"였는데 이제 확인됐다: `12: Declarations. Cards Speak at Showdown` — "Cards speak to determine
  the winner." 승자 판정의 근거 조항이 맞다. 다만 R40 의 **두 번째** 근거("다중 팟이어도 질문은 메인팟이
  누구에게 가는가이고 그건 족보 판정")는 그대로 유효하고, Rule 12 는 족보 판정 조항이므로 오히려 잘 맞는다.
  붙이면 학습자가 근거 조항을 하나 더 얻는다. 엔진 문자열 변경이라 별도 승인 사항.
- **Task 8 #8 · 선택지 라벨 균일화 (실사용 전 권장)** — `decisions.ts:179` 가 정답을
  `"{answer} — 직전 레이즈 폭 {step}만큼 추가"` 로, 오답을 `"직전 벳 총액을 두 배로"` 식으로
  렌더한다. 정답만 규칙 어휘로 표현돼 학습자가 산술 없이 고를 수 있다. 네 선택지를 같은 형태로
  (금액만, 또는 전부 방법명) 통일할 것.

## G. 프로세스 관찰 — 다음 계획에 넘길 것

최종 리뷰가 반대한 판정 4건 중 3건이 같은 모양이다: **태스크 N 에서 내린 판정이 태스크 N+k 가
구현할 동작에 대한 것인데, 착지한 코드에 대고 재검증된 적이 없다.** R22 가 가장 명확한 사례
(전제는 "핸드 내용"에 관한 것인데 `require` 는 "판단 지점"에 대한 약속 — 32.7% 미이행).

값싼 가드: **"X 는 구조적으로 보장된다"고 주장하는 판정은 같은 fix 라운드 안에서
그 X 를 *소비하는 층*에서 단언하는 테스트로 변환한다** — 입력을 *생산하는* 층이 아니라.

이 브랜치는 구조적으로 실패 불가능한 테스트를 4건 출하했고 전부 리뷰에서 잡혔다.
"어떤 구현 변경이 이 단언을 실패시키나"를 매번 묻게 한 것이 그것을 잡았다.
