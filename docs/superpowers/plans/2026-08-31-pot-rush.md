## 0. 결론 먼저

프로토타입에서 재미가 확인된 10문제 러시를 앱으로 옮긴다. **로직은 한 줄도 옮기지 않는다** —
덱·평가·팟분리·홀칩순서·칩분해는 전부 기존 엔진과 뷰 유틸을 부른다. 새로 쓰는 것은
**문제를 만드는 코드**와 **화면**과 **음향**뿐이다.

계획서에서 정한 세 가지(설계 §12 미결정):

| 미결정 | 결정 | 근거 |
|---|---|---|
| `PokerTable` 재사용 범위 | **재사용하지 않는다.** 러시 전용 `RushTable` 을 새로 만든다 | §2 — 코드를 읽고 내린 결론 |
| 카드 에셋 배포 형태 | **개별 파일 52장** (`app/public/cards/<코드>.svg`) | §3 — 실측 |
| 음향 CC0 에셋 출처 | **에셋을 쓰지 않는다. WebAudio 합성** | §4 — 2026-08-31 사용자 승인 |

## 1. 엔진을 정본으로 쓰는 방법 — 홀칩까지 포함해서

가장 중요한 설계 결정이다. **러시는 홀칩 순서를 다시 구현하지 않는다.**

문제는 이거였다: 홀칩 문제에는 보드도 홀카드도 없는데, 정본인 `awardPots` 는 카드를 받아
쇼다운을 평가한 뒤에야 순서를 매긴다. 프로토타입은 그래서 `orderFromButton` 을 베껴 썼다.
앱에서 그걸 반복하면 정본이 둘이 된다.

**해법 — "전원 동점" 히든 픽스처.** 화면에 나오지 않는 카드 배치를 만들어 `awardPots` 를
그대로 부른다:

- 보드 = 브로드웨이 스트레이트 `As Kh Qd Jc Ts`
- 홀카드 = 랭크 2~9 (32장 — 좌석 9개에 18장이 필요하니 충분하다)

이러면 어느 좌석도 보드를 이길 수 없다. 보드와 페어가 안 되니 트리플·풀하우스가 없고,
보드에 같은 무늬가 최대 2장이라 플러시도 안 된다. **전 좌석이 보드로 플레이해 완전 동점**이
되고, 그때 `awardPots` 의 승자 집합은 곧 우리가 넘긴 `eligibleSeats` 다. 남은 100 칩을
받는 좌석이 정답이다.

**실측 확인 (2026-08-31, 이 세션):** 좌석 2~9 전 구간에서 `compareHands` 가 0, 라벨이
`스트레이트`. 좌석 5 · 자격자 {0,2,3} 에서 버튼별 홀칩 수령 좌석 —

```
button=0 odd=2 | button=1 odd=2 | button=2 odd=3 | button=3 odd=0 | button=4 odd=0
```

버튼 왼쪽 첫 자격자부터 시계방향이고, 버튼(2)이 자격자일 때 맨 뒤로 간다. 규칙과 일치한다.

같은 원리로 나머지 넷도 전부 엔진이 답한다:

| 유형 | 정답을 내는 엔진 호출 |
|---|---|
| 사이드팟 분리 | `buildPots(contributed, folded)` 의 `amount` 들 |
| 승자 판정 | `evaluateHand` + `compareHands` |
| 메인팟 지급 | `buildPots` → 메인팟 자격자 중 `evaluateHand` 최고 |
| 스플릿 판정 | `evaluateHand` 동점 집합 |
| 홀칩 배분 | **`awardPots`** (위 픽스처) |

**러시 코드에 포커 규칙은 없다.** 러시가 하는 일은 상황을 만들고, 엔진에 물어보고,
그 답을 화면에 내는 것뿐이다.

## 2. `PokerTable` 은 재사용하지 않는다 — 코드를 읽고 내린 결론

`app/src/components/table/PokerTable.tsx` 와 `Seat.tsx` 를 읽었다. 재사용을 막는 이유가 셋이다.

1. **입력이 `HandState` 다.** 러시 문제는 핸드가 아니다. 사이드팟 문제에는 쇼다운이 없고
   홀칩 문제에는 보드가 없다. `HandState` 를 지어내려면 `reduce.ts` 에 이벤트를 흘려야 하는데,
   그건 "핸드를 통째로 만들지 마라"는 설계 §3 을 정면으로 어긴다
2. **좌석 배치가 타원 절대좌표**(`seatOffset`, `LAYOUT_W/H` 고정 종횡비)다. 설계 §8 이 못박은
   러시 배치는 **5열 그리드**다 — 좁은 화면에서 좌석이 겹치지 않는 것이 그 배치의 존재 이유고,
   프로토타입이 그 배치로 재미 게이트를 통과했다
3. **`Seat` 은 `SeatState.revealed` 로만 카드를 연다.** 러시에는 `revealed` 개념이 없다 —
   유형마다 공개 규칙이 다르다(사이드팟은 전원 뒷면, 쇼다운 유형은 전원 앞면)

그래서 **재사용 경계를 이렇게 긋는다**:

| 대상 | 결정 |
|---|---|
| `chipBreakdown` · `CHIP_UNITS` (`components/table/chips.ts`) | **그대로 재사용.** 칩 분해 규칙은 하나다 |
| `globals.css` 디자인 토큰 | **그대로 재사용.** 색을 하드코딩하지 않는다 |
| `PokerTable` · `Seat` · `geometry.ts` | 재사용 안 함 (위 셋) |
| `Card` | 재사용 안 함 — 글자로 그리는 카드다. 러시는 CC0 에셋을 쓴다 |
| `ChipStack` | 재사용 안 함 — 단위당 원반 1개 + 숫자다. 러시는 실물처럼 쌓인 더미다 |

**기존 시뮬레이터 화면은 손대지 않는다.** 카드 에셋을 그쪽에 소급 적용하지 않는다 — 범위 밖이다.

## 3. 카드 에셋 — 개별 파일 52장 (실측 근거)

프로토타입의 인라인 스프라이트(1,588,565 bytes)를 52개 파일로 되돌려 `app/public/cards/` 에 둔다.

**실측 (2026-08-31, 이 세션, gzip -9):**

| 배포 형태 | 전송량 | 언제 |
|---|---|---|
| 스프라이트 1개 | **303 KB (gzip)** | 첫 화면에서 전부 |
| 개별 52장 합계 | 330 KB (gzip) | 실제로는 화면에 뜬 카드만 |
| 개별 · 카드 1장 평균 | 6.5 KB (gzip) | |
| 개별 · 최대 (`KH`) | 29 KB (gzip) | 그림카드 |
| 개별 · 최소 (`AD`) | 0.5 KB (gzip) | 핍카드 |

한 문제에 보이는 카드는 많아야 15장(보드 5 + 홀 5×2) ≈ **100 KB 안쪽**이다. 스프라이트는
첫 문제에 303 KB 를 전부 낸다.

**결정적인 이유는 따로 있다.** 외부 SVG 를 `<use href="/cards/sprite.svg#c-AS">` 로 부르는 것을
Chromium 이 지원하지 않는다. 스프라이트를 쓰려면 JS 로 받아 DOM 에 주입해야 하고, 그러면
"인라인 1.6MB 를 쓰지 마라"(설계 §8)를 우회로 되살리는 꼴이 된다.

개별 파일은 `<img src="/cards/AS.svg">` 하나로 끝난다 — JS 없음, 캐시는 브라우저가 한다.

- 파일명: `<랭크><무늬 대문자>.svg` (`AS`, `TD`, `2C`). 엔진 `Card` 가 `suit: 's'|'h'|'d'|'c'` 이므로
  코드는 `card.rank + card.suit.toUpperCase()`
- 분리 스크립트를 `docs/superpowers/prototypes/assets/split-card-sprite.py` 로 커밋한다.
  나중에 "이 파일들 어디서 났나"의 답이 된다
- 카드 뒷면은 지금처럼 CSS 로 그린다 (Commons 뒷면은 LGPL — `CREDITS.md` 에 이미 기록됨)
- `CREDITS.md` 를 `app/public/cards/CREDITS.md` 로 복사하고 배포 형태 변경을 추기한다

## 4. 음향 — 에셋 없이 WebAudio 로 합성한다 (승인됨)

설계 §7 은 "에셋은 CC0만"이라고 적었다. **더 나은 답은 에셋을 아예 안 쓰는 것**이라고 본다.

| | CC0 녹음 에셋 | **WebAudio 합성 (권장)** |
|---|---|---|
| 라이선스 근거 | 배포처 페이지를 받아 기록해야 함 | **필요 없음 — 코드가 소리를 만든다** |
| 전송량 | 4종 × 수십 KB | **0 바이트** |
| 로딩 실패 | 있음 (조용히 꺼야 함) | 없음 (`AudioContext` 생성 실패만) |
| 소리 질 | 실사 녹음 | 합성음 — 칩·카드는 노이즈 버스트라 합성이 잘 먹는다 |

네 소리 전부 짧은 효과음이라 합성으로 충분하다:

- **카드 슬라이드** — 화이트 노이즈 60ms + 밴드패스 스윕
- **칩** — 노이즈 25ms × 3회 + 고역 링잉
- **타이머 틱** — 사인 1200Hz 30ms
- **정답 / 오답** — 상행 2음 / 하행 단2도

지킬 것은 설계 §7 그대로다: 첫 사용자 입력 전 무음(`AudioContext` 를 그때 만든다),
음소거 토글은 `localStorage`, `prefers-reduced-motion` 과 분리, 실패하면 조용히 끄고 게임은 계속.

> **결정 (2026-08-31, 사용자 승인)**: 합성으로 간다. `CREDITS.md` 에
> "음향은 외부 에셋 없음(코드 합성)"이라고 적는다.

## 6. 문제 타입과 결정론

```ts
type RushQuestion =
  | { kind: 'sidepots'; ...; fields: { label: string; answer: number }[] }
  | { kind: 'winner' | 'payout' | 'oddchip'; ...; answerSeat: number }
  | { kind: 'split'; ...; answerSeats: number[] }
```

공통 필드: `label`(유형명) · `prompt` · `limitSec` · `seats` · `board` · `buttonSeat` · `pot?` · `why`.

- **무작위는 `createRng(seed)` 만 쓴다.** `Math.random()` 금지 — 같은 시드는 같은 10문제를 낸다.
  URL `?seed=` 는 `simulator/page.tsx` 선례를 따른다 (일일 챌린지는 4단계지만 문은 열어둔다)
- 재생성 루프에는 **상한을 둔다**(유형당 60회). 넘으면 시드를 한 칸 밀어 다시 —
  무한 루프는 러시에서 화면 정지로 나타난다
- 문제 배분: `[사이드팟×3, 승자×2, 지급×2, 스플릿×2, 홀칩×1]` 을 섞는다 (프로토타입 확정,
  한 유형 상한 4를 자동으로 만족)
- 제한시간: 45 / 28 / 40 / 30 / 20초 (설계 §4)
- 딜러 버튼은 **모든 유형에 표시**한다 (홀칩 문제에만 나오면 유형이 새어나간다)

**타이머는 시각 기준으로 센다.** 프로토타입은 100ms 인터벌마다 `t -= 0.1` 을 했는데,
점수가 남은 시간에 비례하므로 드리프트가 곧 점수 오차다. `performance.now()` 로 마감 시각을
잡고 매 틱마다 남은 시간을 계산한다.

## 7. 테스트 — 생성기와 채점기를 같은 코드로 확인하지 않는다

설계 §5.4 의 핵심이다. 생성기가 엔진을 부르므로, 테스트는 **다른 경로로 답을 다시 구해** 맞춘다.

| 대상 | 방법 | 독립성 |
|---|---|---|
| 사이드팟 금액 | 1,000판 × **칩을 한 단위씩 나눠 담는 오라클**로 재계산 | `buildPots` 의 층 자르기와 알고리즘이 다르다 |
| 사이드팟 합계 | 팟 합 = 투입액 합 | 불변식 |
| 승자·지급·스플릿 | 1,000판 × `awardPots` 로 재계산해 정답 집합 일치 | 생성기는 `compareHands` 루프, 검증은 `awardPots` — 진입점이 다르다 |
| 스플릿 | 정답이 항상 2명 이상 · 카드 중복 0 · 정답 좌석이 특정 인덱스에 쏠리지 않음 | |
| 홀칩 순서 | **좌석 2~9 × 버튼 × 공집합 아닌 자격자 집합 전수 8,148건** (Σ n·(2ⁿ−1), n=2..9) | `awardPots` 대 손으로 쓴 시계방향 오라클 |
| 홀칩 문제 | 1,000판 × 잔여가 정확히 100 하나 · **버튼이 자격자가 아닌 판이 실제로 나온다** | 설계 §5.2 |
| 사이드팟 난이도 | 올인 금액 < 콜 금액 (층이 눈에 보인다) | 설계 §5.3 |
| 카드 중복 | 전 유형 1,000판, 한 판 안에 같은 카드 0 | |
| 점수 | 3연속 1.5배 · 5연속 2배 경계, 오답이 연속을 끊는다 | 단위 테스트 |
| 문제 세트 | 10문제 · 5종 전부 · 유형 상한 4 · 같은 시드면 같은 세트 | |

vitest 는 `environment: 'node'` · `include: src/**/*.test.ts` 다. **컴포넌트 테스트 환경이 없고
이번에 도입하지 않는다** — 렌더 검증은 §8 처럼 실제 브라우저로 한다.

## 8. 렌더 검증 — 실제 브라우저로 눈으로 본다

프로토타입에서 **정적 검사로는 하나도 안 잡히고 렌더로만 잡힌 결함이 다섯**이었다
(정답 금액 미리 보임 · 칩 더미 넘침 · 인라인 스타일이 칩 텍스처를 지움 · 피드백이 버튼 아래 ·
덱이 안 보임). 그래서 마지막 단계는 `npm run dev` + Playwright 로 실제 렌더를 본다.

- 360px · 560px 두 폭에서 스크린샷, **가로 넘침 0** (`scrollWidth <= clientWidth`)
- 10문제 자동 완주 — 5종 전부 출제되고 결과 집계가 맞는지
- 사이드팟 문제에서 **정답 금액이 채점 전 DOM 어디에도 없는지**
- 카드 에셋이 실제로 뜨는지 (404 면 빈 칸이 되는데 정적 검사로는 안 보인다)
- 기록이 새로고침 뒤에도 남는지
- 첫 입력 전 무음 · 음소거 토글

## 9. 단계와 검증 (단계마다 실행 출력으로 확인)
