## 이 계획이 만드는 것

시드 하나로 노리밋 홀덤 핸드를 결정론적으로 생성하고, 판단 지점 4종

순수 TypeScript 엔진. UI는 이 계획에 없다.

## 무엇을 중점적으로 봐야 하나

**최우선 — 포커 규칙이 정확한가.** 이건 훈련 제품이다. 엔진이 틀린 판정을 하면
사용자가 틀린 것을 배우고, 그걸 현장에서 쓴다. 다른 어떤 결함보다 심각하다.
계획서에 박혀 있는 구현 코드를 실제 TDA 규정과 대조해줘. 특히:

- evaluateHand 의 스트레이트 판정 — 휠(A-2-3-4-5), A-high, 스트레이트 플러시 경계
- buildPots 의 층 분리 — 폴드한 사람의 데드머니, 블라인드를 낸 사람이 그대로
  올인했을 때의 처리
- minRaiseTo 의 lastRaiseSize 초기값과 갱신 시점 (Rule 43-A)
- interpretChipPush 가 Rule 45-A 를 정확히 구현하는가
- validateAction 의 언더콜 처리 (Rule 51-B — 오픈 벳과 그 외가 다르다)

**둘째 — 생성기가 합법적인 핸드를 만드는가.** runBettingRound 가 만드는
이벤트 시퀀스가 실제 포커에서 성립하는지 봐줘. 액션 순서, 라운드 종료 조건,
올인 이후 처리, 스트리트 전환. 여기서 불법 핸드가 나오면 그 위의 모든 판단
지점이 오염된다.

**셋째 — 테스트가 실제로 검증하는가.** 구현을 보고 뒤따라 쓴 테스트(통과가
보장된 테스트)가 있는지 봐줘. 특히 기대값이 구현 로직을 그대로 옮긴 것이라면
그건 검증이 아니다.

**넷째 — 태스크 사이의 타입·이름 일관성.** Task N 이 만든 이름을 Task M 이
다르게 부르는 곳이 있는지. index.ts 재수출 목록이 실제 export 와 맞는지.

## 이 프롬프트를 이렇게 쓴 이유

**"구현하지 마"를 명시했다.** 계획서를 주면 실행하고 싶어지는데, 이번 세션의
목적은 검토다. 산출물을 "개선된 계획서"로 못 박았다.

**포커 규칙 정확성을 최우선으로 올렸다.** 훈련 제품이라 엔진이 틀리면 사용자가
틀린 것을 배운다. 일반적인 코드 리뷰 우선순위(성능·구조)와 다르다.

**이미 고친 4건을 알려줬다.** 같은 걸 다시 찾느라 시간 쓰지 않게. 다만 "고친
방식이 맞는지는 봐도 좋다"로 열어뒀다.

**의심 지점을 "단정하지 말고 확인만"으로 줬다.** 내가 틀렸을 수 있어서, 확신을
심어주면 오히려 검토를 방해한다.

**"못 찾았으면 못 찾았다고 하라"를 넣었다.** 없는 문제를 만들어내는 것이
검토에서 가장 흔한 실패다.
