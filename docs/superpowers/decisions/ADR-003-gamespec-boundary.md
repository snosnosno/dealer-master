# ADR-003 — `GameSpec` 은 데이터, `Ruleset` 은 판정. `Street` 은 건드리지 않는다

- **날짜**: 2026-09-01
- **상태**: 채택
- **관련**: `PRD.md` §6-3 · §10 · [ADR-002](ADR-002-run-mode-dropped.md)

---

## 결정

축 3(믹스게임)을 시작하기 전에 세 가지를 못박는다.

1. **`GameSpec` 이 게임 데이터의 정본이다.** `Ruleset` 의 데이터 필드
   (`family` · `bettingStructure` · `holeCardCount` · `streets`)는 `GameSpec` 으로 옮기고,
   `Ruleset` 은 **판정 메서드만** 남긴다.
2. **`Street` 타입(`'preflop' | 'flop' | 'turn' | 'river'`)은 지금 손대지 않는다.**
   `GameSpec.streets[].id` 는 자기 문자열을 쓴다.
3. **평가기(승자 판정)는 2단계에 만들지 않는다.** PRD §10 대로 3단계다.

---

## 맥락

PRD §6-3 이 `GameSpec` 을 정의하면서 기존 `Ruleset` 인터페이스와 필드 넷이 겹쳤다.
둘 다 두면 "이 게임의 홀카드가 몇 장인가"의 정본이 두 곳에 생긴다. 이 레포가 이미
한 번 당한 실패다 — 리오픈 규칙이 `generate.ts` 와 `bots.ts` 에 사본으로 살아 있었고,
그 사본이 규정과 어긋나 있었다(ADR 아님, `2026-09-01-action-rush.md` §1).

## 근거

### 1. 두 타입은 서로 다른 질문에 답한다

| | 무엇에 답하나 | 형태 |
|---|---|---|
| `GameSpec` | **이 게임이 무엇인가** — 카드 몇 장, 어느 스트릿, 강제 베팅은 무엇 | 데이터 |
| `Ruleset` | **이 액션이 합법인가** — 최소 레이즈, 칩 해석, 리오픈 | 코드(메서드) |

축 3 의 2단계 문제(홀카드 수·브링인·액션 순서·번카드·베팅 구조·드로우)는 전부 앞의 질문이다.
`Ruleset` 을 구현하지 않고도 낼 수 있다. **문제 생성기가 스펙 필드에 1:1 대응한다**는
PRD §6-3 의 이득이 여기서 나온다.

### 2. 데이터 필드를 옮기는 비용이 지금은 거의 0 이다

`Ruleset` 의 데이터 필드를 실제로 읽는 곳은 **`integration.test.ts` 의 `nlh.holeCardCount`
한 줄뿐**이다 (`grep '\.streets\|\.holeCardCount\|\.family\|\.bettingStructure'` 로 확인).
`streets` · `family` · `bettingStructure` 는 선언만 돼 있고 아무도 읽지 않는다.
지금 옮기면 한 줄, 팟리밋 룰셋이 생긴 뒤에 옮기면 세 구현을 동시에 고쳐야 한다.

### 3. `Street` 을 넓히면 엔진 전체가 흔들린다 — 그런데 아직 이유가 없다

`Street` 은 `HandState.street` 과 `HandEvent` 가 쓴다. 넓히려면 노리밋 홀덤 시뮬레이터
전체가 새 값을 견뎌야 한다. 그런데 **축 3 의 2단계는 핸드를 시뮬레이션하지 않는다** —
문제는 "이 스트릿의 첫 액션은 누구인가" 같은 구조 질문이고, `HandState` 가 필요 없다.

스터드 핸드를 실제로 굴려야 할 때(승자 판정·사이드팟) 그때 넓힌다. 그때는 무엇이
필요한지 알고 넓히게 된다. PRD §6-3 의 함정 1 — *"쓰이지 않는 필드는 검증되지 않은 채
굳는다"* — 이 타입에도 그대로 적용된다.

---

## 이번 결정에 포함되지 않는 것 (사용자 결정, 2026-09-01)

자료(Mix Game Guide · Mixed Games Rules)를 읽고 나온 두 제안을 **반영하지 않기로** 했다.
스펙을 처음부터 완전하게 만들지 않는다는 원칙과 같은 방향이다.

| 제안 | 결정 | 그래서 지켜야 할 것 |
|---|---|---|
| 7-Card Stud 4th street 오픈페어 → 빅벳 **선택** 가능. `sizeMultiplier: 1 \| 2` 로는 조건부를 못 담으니 필드를 추가하자 | **추가하지 않는다** | **"지금 최대 벳은?" 문제에서 4th street 오픈페어 상황을 출제하지 않는다.** 생성기에서 피하지 않으면 스펙과 정답이 어긋난다 |
| 게임 전환 규칙(레드·그린 버튼, 좌석 수만큼)이 프로토콜에 있으니 그대로 쓰자 | **쓰지 않는다** | 전환 주기는 PRD §6-3 대로 **프로토타입에서 정한다.** "지금 게임이 바뀌나?" 유형은 만들지 않는다 |

---

## 결과

- 새 디렉터리 `lib/mixgame/` — `GameSpec` 타입과 게임별 스펙 파일이 여기 산다
- `rulesets/types.ts` 의 `Ruleset` 에서 데이터 필드 넷을 걷어낸다.
  `nlh.ts` 와 `integration.test.ts` 가 함께 바뀐다.
  **실행은 `GameSpec` 을 처음 쓰는 커밋에서 함께 한다** — 먼저 걷어내면 홀카드 수가
  어디에도 없는 구간이 생기고, 그 구간에서 테스트가 숫자를 지어내게 된다
- `Street` · `HandState` · `HandEvent` 는 그대로
- 스펙을 먼저 쓸 게임은 PRD §10 대로 **성격이 가장 다른 둘** — 7-Card Stud 와 2-7 Triple Draw.
  규칙 사실은 [`docs/references/mixgame-facts.md`](../../references/mixgame-facts.md) 에 정리돼 있다

## 스펙을 실제로 적어 보고 나온 것 (2026-09-01, 프로토타입)

`deal: number` + `faceUp: boolean` (PRD §6-3 초안)으로는 **스터드 3번가를 표현할 수 없다.**
한 스트릿이 다운 2장과 업 1장을 동시에 내리기 때문이다. 프로토타입은 `deal: { down, up }`
으로 적었고 두 게임 모두 표현됐다. 앱으로 옮길 때 이 모양을 쓴다.

PRD §10 이 2단계와 3단계를 나눈 이유가 이것이다 — 평가기를 만들기 전에 알았다.

## 뒤집힐 수 있는 지점

스펙 두 개를 써 보고 **`GameSpec` 이 두 게임을 표현하지 못하면** 이 결정이 아니라
스펙의 모양이 틀린 것이다. 그때는 평가기를 만들기 전이라 손해가 작다 (PRD §10 이
2단계와 3단계를 나눈 이유다).
